# 03장 보충. 거스름돈을 직접 맞혀 보기

날짜: 2026-11-12

시작 기준: `85415bb` — 거스름돈 계산과 실기기 자동 검증 추가. 사용자가 이 커밋의 GitHub 업로드를 확인한 뒤 진행했다.

## 목표와 놀이 순서

충분한 놀이돈을 고르면 거스름돈 문제가 나타난다. 아이가 답을 입력하고 “정답 확인”을 누르면 채점한다. 정답을 맞힌 뒤 받을 거스름돈과 계산식을 공개한다.

1. 물건을 담고 충분한 놀이돈을 고른다.
2. 물건값과 낼 돈을 보고 거스름돈을 숫자로 입력한다.
3. 오답이면 뺄셈 힌트를 읽고 답을 고쳐 다시 확인한다.
4. 정답이면 계산식과 남을 돈을 확인한다.
5. “다시 풀기”로 같은 문제를 새로 풀거나 물건·놀이돈을 바꾼다.

빈 답은 입력 안내를 보여 주며 0원으로 채점하지 않는다. 정확히 낸 문제는 숫자 0을 입력해야 정답이다. 입력은 1~5자리 숫자만 받으며, 소수점·음수·쉼표·지수 표기·공백·문자는 숫자로 조용히 바꾸지 않고 잘못된 입력으로 처리한다. 숫자 키보드를 사용하되 채점 로직에서도 형식을 검사한다.

## 정답을 미리 보이지 않게 하기

계산 결과 카드는 정답 이후에만 표시한다. 낼 돈을 10,000원으로 고르면 하단의 예산 잔액도 거스름돈과 같으므로, 푸는 동안 하단 금액을 ?원으로 가리고 “거스름돈을 맞히면 남을 돈을 보여 줘요.”라고 안내한다. 접근성 라벨에서도 잔액과 기존 힌트를 숨긴다. 장바구니 합계와 오늘의 예산은 계속 표시한다.

정답을 맞히면 기존 계산식과 예산 잔액이 돌아온다. 예산 자체를 차감하거나 결제 완료로 처리하지 않는다. 당근 1개 1,000원에 5,000원을 선택한 문제는 정답 4,000원과 예산 잔액 9,000원이 다름을 확인하는 사례다.

## 상태와 핵심 코드

`ShoppingState`에 `quiz: { answer, status }`를 추가했다. 상태는 unanswered·invalid·incorrect·correct로 구분한다.

- `change-quiz.ts`: 입력 형식과 정답을 판단하는 순수 함수와 상태 타입을 정의한다.
- `payment.ts`: 답 수정·채점·다시 풀기와 기존 쇼핑 동작을 하나의 reducer에서 처리한다.
- 실제 상품 구성 또는 낼 돈이 바뀌면 퀴즈도 동시에 초기화한다. 선택 취소·전체 비우기·재실행도 초기화한다.
- 같은 돈 선택·9개 상한·없는 품목 삭제처럼 변화가 없는 동작은 풀이를 보존한다.
- 정답 이후 입력과 재채점은 잠그고, 다시 풀기를 누르면 답과 안내만 초기화한다. 상품과 낼 돈은 보존한다.
- `change-quiz.tsx`: 제어된 숫자 입력, 채점·힌트·정답 안내·다시 풀기 버튼을 표시한다.
- `App.tsx`: 새 초기 상태와 액션을 연결하고, 정답 전 하단 잔액을 가린다.

핵심 처리 이유는 한국어 주석으로 남겼다. 형식 검사에서 Number('')가 0이 되는 문제를 피하고, 0원 정답과 미입력을 명확히 구분한다. 새 패키지나 DB는 추가하지 않았다.

## 키보드와 화면 조작

TextInput은 숫자 키보드와 최대 5자리 입력을 사용한다. FlatList에 keyboardShouldPersistTaps="handled"를 설정해 키보드가 열린 상태에서 채점 버튼을 누른 첫 탭이 전달되게 했다. 채점·다시 풀기·돈 선택을 처리할 때 Keyboard.dismiss()로 키보드를 닫는다. KeyboardAvoidingView로 키보드가 열린 화면의 공간을 조정한다.

정답 전후의 입력 가능 상태를 접근성 상태로도 표시한다. 화면의 모든 입력과 버튼을 하나의 접근성 요소로 묶지 않고 각각 조작할 수 있게 둔다.

## 실제 코드 검증과 자동 검사

담당 코어 파일의 단위 검사는 장바구니 9개·예산 8개·돈 선택 및 퀴즈 상태 27개·입력 채점 5개, 총 **49개 모두 통과**했다. 코어 파일 ESLint·타입 진단도 통과했다. UI 연결 후 앱 전체에서 다음 명령을 실행했고 둘 다 통과했다.

```bash
cd apps/mobile
npm run typecheck
npm run lint
```

핵심 테스트의 실제 Node 명령은 다음과 같다. package.json의 npm test에도 네 파일을 등록했다.

```bash
node --experimental-strip-types --test src/features/cart/cart.test.ts src/features/budget/budget.test.ts src/features/payment/payment.test.ts src/features/payment/change-quiz.test.ts
```

기존 MODULE_TYPELESS_PACKAGE_JSON 경고는 있었지만 검사 실패는 아니었다. 연결 사전 검사인 npm run device:doctor도 준비 완료로 종료했다. 이 사전 결과는 화면 검사 통과를 뜻하지 않는다.

Maestro는 첫 문제에서 빈 답 제출·오답·수정·정답·다시 풀기를 검사하고, 다른 정상 계산 사례에서는 solve-quiz.yaml을 재사용한다. 0원 정답, 9,000원 오답과 4,000원 정답, 정답 전 잔액 숨김, 상품·돈 변경 초기화, 무변화 동작의 풀이 유지와 재실행도 검사한다. 이전 장바구니·예산·돈 선택·계산식 검증을 유지한다.

전체 검사와 커밋 명령:

```bash
npm run verify:device -- --message "feat: 거스름돈 맞히기와 자동 검증 추가"
```

실기기 성공 여부는 이 변경과 함께 저장되는 [최종 검증 기록](../verification/latest-android.md)에서 실행 기준 HEAD·시각·검사 결과로 확인한다. 이 원고를 작성할 때 아직 수행하지 않은 실기기 검사는 성공으로 기록하지 않았다. 실행기는 모든 검사에 통과한 같은 소스와 원고만 커밋한다.

원본 로그·스크린샷은 Git에서 제외한 .artifacts/device에 남긴다. 정답 판정은 놀이 기능이며 실제 금전 결제·아이 정보 수집·서버 전송은 수행하지 않는다. iPhone 실기기와 TalkBack 음성 읽기는 별도 검증이 필요하다.

## 첫 전체 실행에서 발견한 검사 파일 형식 문제

전체 자동 실행에서 앱 테스트 49개·커밋 보호 테스트 9개·타입·ESLint·세 플랫폼 번들은 통과했다. 그러나 Maestro 2.12.1이 solve-quiz.yaml의 direction 변수 표기를 형식 오류로 거부했다. 일반 YAML 구문 검사는 통과했지만 Maestro 명령의 방향 열거형은 같은 방식으로 변수를 받을 수 없었다. 실제 화면 명령은 시작하지 않았고 자동 커밋도 만들지 않았다. 임시 화면 유지 설정은 원래 값으로 복원되었다.

스크롤 방향을 호출 위치의 고정 UP/DOWN 명령으로 옮기고, 공통 helper는 입력칸이 보이는 상태부터 채점 절차를 수행하도록 수정한다. 이 수정 이후 같은 전체 검사 명령을 다시 실행하며 최종 성공 결과는 자동 생성 검증 문서에 남긴다.

수정 후 Maestro 2.12.1의 check-syntax 명령으로 payment.yaml과 solve-quiz.yaml 모두 OK, 종료 코드 0을 확인했다. 자동 실행기에도 두 명령의 형식 검사를 먼저 추가해, 다음부터 기기 설정 변경과 앱 코드 검사 전에 같은 오류를 찾도록 했다.

```bash
maestro check-syntax apps/mobile/.maestro/payment.yaml
maestro check-syntax apps/mobile/.maestro/solve-quiz.yaml
```

## 키보드가 채점 버튼을 가린 문제

다음 전체 실행에서는 Maestro 형식 검사와 코드 검사를 통과하고 실제 갤럭시 조작을 시작했다. 첫 빈 답 검사에서 숫자 키보드가 열리자 입력칸 아래의 정답 확인 버튼이 고정 장바구니 요약 뒤로 밀려 보이지 않았다. 입력칸은 보였지만 버튼을 찾지 못해 검사가 실패했고, 커밋은 실행되지 않았다.

채점 버튼을 입력칸과 같은 줄로 옮겨 키보드가 열린 상태에서도 두 요소를 함께 볼 수 있게 했다. 버튼의 화면 글자는 두 줄 “정답 / 확인”이고 접근성 이름은 “정답 확인”으로 유지했다. 입력 안내는 좁은 화면에 맞게 “답 입력”으로 줄였다. 실제 기기에서 발견한 가림 문제이므로 테스트에서 키보드를 먼저 닫아 우회하지 않고 동일한 빈 답 시나리오로 다시 확인한다.

## 수량 상한 검사에서 스크롤 위치 보완

채점 버튼 배치를 수정한 실행에서는 키보드가 열린 상태의 빈 답 제출, 오답 수정, 정답 공개, 다시 풀기, 0원, 거스름돈 4,000원과 예산 잔액 9,000원 구분까지 통과했다. 이후 수량 상한에서 비활성 추가 버튼을 누른 뒤 상품 카드의 “당근 9개 담김” 글자를 찾는 검사에서 실패했다.

실패 화면의 장바구니와 하단 합계는 당근 9개·9,000원으로 유지되었다. 상품 카드의 수량 글자는 화면 위로 벗어나 있었으므로, 추가 버튼이 보이는 위치와 수량 글자가 보이는 위치를 같다고 가정한 검사 문제였다. 비활성 버튼을 누르는 검사는 유지하고, 그 뒤 수량 글자까지 명시적으로 스크롤한 다음 9개 유지 여부를 확인하도록 보완한다. 이 실행도 전체 성공으로 기록하거나 커밋하지 않았다.

## 품목 삭제 버튼과 Expo Go 개발 메뉴의 겹침

수량 상한 스크롤을 보완한 다음 실행에서는 9개 제한의 무변화와 수량 감소 후 새 문제의 정답 2,000원까지 통과했다. 그러나 당근 8개를 지우는 마지막 품목 삭제 검사에서 장바구니가 그대로 남았다. 실패 스크린샷에는 Expo Go 개발 메뉴가 열려 있었다. 위로 스크롤하며 삭제 버튼을 화면 오른쪽 위에 걸치게 둔 탓에 자동 터치가 앱의 삭제 동작에 도달하지 못했다.

이 실행은 실패로 종료했으며 커밋을 만들지 않았다. 검사 중 적용한 화면 유지 값은 7에서 원래 값 0으로 복구됐다. 삭제 뒤 0개·0원과 문제 초기화를 확인하는 조건은 유지하고, 삭제 버튼의 위치를 보완한 뒤 해당 구간부터 실기기에서 재현 확인한다.

삭제 버튼을 위로 찾는 두 지점에만 centerElement: true를 적용했다. 버튼을 화면 안쪽으로 이동시켜 Expo Go 개발 메뉴와 겹치지 않게 한 것이다. 다른 스크롤과 삭제 결과 조건은 유지했다.

전체 재검사 전에 이전 실행의 메모리 상태에서 Expo 메뉴를 닫고, 수정한 동일 삭제 구간을 실기기로 따로 실행했다. 12개 명령이 종료 코드 0으로 통과했으며 당근 8개·8,000원에서 삭제 후 0개·0원, 남을 돈 10,000원, 돈 선택 없음, 퀴즈·거스름돈 결과 사라짐을 확인했다. 새 서버나 USB 포트 연결은 만들지 않았고 화면 유지 값도 원래대로 복구했다. 원본은 Git에서 제외한 `.artifacts/device/tail-delete-20261111T190722486Z/`에 남겼다. 이 부분 검사를 전체 성공으로 대신하지 않고, 같은 소스로 전체 자동 검사와 커밋 절차를 다시 실행한다.
