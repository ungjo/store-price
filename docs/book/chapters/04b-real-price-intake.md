# 04장 보충. 실제 가격을 비공개 관측으로 기록하기

날짜: 2026-11-12

시작 커밋은 `1f994f3`(Supabase 공개 상품 목록 읽기 연결)이다. 사용자가 갤럭시에서 “가게에서 불러온 상품이에요.”와 예시 상품 6개를 확인하고 GitHub 업로드를 마친 뒤, 실제 SSG.COM 이마트 가격의 DB 저장·자동 검사·개발 기록·커밋을 요청했다.

이번 단계는 소수 상품의 화면에서 확인한 가격을 비공개 DB 이력으로 보관하는 작업이다. 실제 가격을 어린이 앱에 공개하는 단계와 구분한다. 실제 상품 자료는 이 원고·seed·검사 fixture에 넣지 않으며, 저장소에는 코드와 검증 방법을 남긴다.

## 검색 가격과 직접 확인한 가격 구분하기

공식 이마트몰 상세 페이지 3개를 브라우저에서 직접 열어 상품명·규격·표시 금액·상품 번호·재고 표시를 읽었다. 검색 도구의 결과는 캐시된 내용일 수 있었고, 실제로 한 후보의 검색 가격과 현재 상세 페이지의 가격이 달랐다. 따라서 검색에서 읽은 값을 현재 시각에 관측한 가격으로 기록하지 않았다.

페이지의 상품 단위 금액과 카드혜택가·회원 적립금은 구분했다. 별도 로그인이나 배송지를 설정하지 않았으므로 특정 배송지의 판매 가능 상태나 오프라인 점포 가격으로 해석하지 않았다. 페이지에 품절이 명시된 상품은 그 상태를 남기고, 배송지별 판매 가능 여부가 확인되지 않은 자료는 unknown으로 기록하는 방식을 택했다.

이번 관측은 확인한 상품 3개에 한정한다. 반복 수집기나 자동 갱신 일정을 만들지 않았으며, 원본 이미지·리뷰·상세 설명도 저장하지 않았다. 실제 상품의 이름·가격·식별자·출처 주소를 포함한 입력과 적재 SQL은 Git에서 제외된 `.artifacts/catalog/`에서 관리한다.

## 저장과 앱 공개를 분리한 이유

앞 단계의 DB는 자체 예시 또는 승인된 API·파일이라는 출처를 요구했다. 공개 페이지를 직접 본 기록을 승인된 API 자료라고 넣으면 출처가 사실과 달라진다. 이를 해결하기 위해 `manual_observation`이라는 별도 출처를 추가한다.

| 항목 | 직접 확인한 관측의 저장 규칙 |
| --- | --- |
| is_sample | false — 실제 페이지에서 확인한 자료 |
| source_kind | manual_observation |
| rights_status | unknown — 앱 이용 범위를 확인했다고 표시하지 않음 |
| publication_state | draft — 공개 목록에서 제외 |
| 상품 is_active | false로 시작 |
| source_price_krw / play_price_krw | 같은 원 단위 정수, 반올림하지 않음 |
| observed_at | 상세 화면을 확인한 실제 시각 |
| source_product_id / source_url | 확인한 상품과 주소를 연결 |
| store_id | 확인하지 않은 점포는 NULL |
| valid_from / valid_until | 확인하지 않은 행사 기간은 NULL |
| display_until | 관측 시각으로부터 24시간인 내부 기한 |

내부 기한은 판매자가 해당 시간까지 같은 가격을 보장한다는 뜻이 아니다. 기한이 지나도 관측 이력은 보존되며, 이 기한을 정했다고 draft 관측이 공개되는 것도 아니다.

이 프로젝트는 초기부터 실제 자료의 앱·책·GitHub 이용 범위를 구분해 확인하도록 설계했다. 공식 페이지의 고지와 접근 가능 여부만으로 이용허락을 받았다고 판단하지 않는다. 여기서 비공개 상태를 유지하는 것은 그 기존 설계의 적용이며, 소량의 가격 사실 저장에 대한 법적 결론을 내리는 것은 아니다. 데이터 제휴 문의는 전송하지 않았다. [가격 자료 조사와 문의 초안](../../03-price-data.md)

DB 제약은 manual_observation을 unknown·draft로만 허용한다. 관리자 역할로 직접 SQL을 실행해도 이 출처를 app_approved·published로 바꿀 수 없다. 이후 승인된 제공 자료를 받으면 기존 관측을 고치는 대신 새 관측을 작성한다. 원본 사실을 덮어쓰지 않는 앞 장의 방침을 유지한다.

## DB 변경 파일 만들기

Supabase 연결 도구가 이번 작업에서 제공되어 프로젝트 목록과 기존 테이블 구조를 조회할 수 있었다. `store-price`의 정상 상태와 자체 예시 6개를 확인했다. 앞 단계에서 연결 도구를 사용할 수 없어 SQL Editor로 확인했던 과정과 구분한다. 기존의 다른 프로젝트에는 변경을 적용하지 않는다.

공식 Supabase CLI 버전을 조회한 결과는 3.1.0이었다. 실제로 실행한 명령은 아래와 같다. 사용자 재현 명령은 Git Bash 표기로 적었으며, 이번 Windows 실행에서는 npm·npx의 `.cmd` 진입점을 사용했다.

```bash
npm view supabase version
npx --yes supabase@3.1.0 --help
npx --yes supabase@3.1.0 migration --help
npx --yes supabase@3.1.0 migration new --help
npx --yes supabase@3.1.0 migration new manual_price_observations
```

CLI가 처음 생성한 파일은 `supabase/migrations/20261112102354_manual_price_observations.sql`이다. 내용을 검토한 뒤 Supabase 연결 도구의 apply_migration으로 원격 적용했으며, 도구가 기록한 버전은 `20261112102641`이었다. 같은 변경의 로컬 파일을 `supabase/migrations/20261112102641_manual_price_observations.sql`로 맞췄다. 원격 list_migrations에서 새 변경 1건을 확인했다.

처음 만든 스키마 파일을 수정하지 않고 이 후속 변경을 추가했다. 변경은 출처와 관측 조건을 확장하며 기존 권한·RLS·공개 뷰·예시 행은 유지한다. 최초 스키마는 사용자가 SQL Editor로 직접 적용한 상태여서 마이그레이션 이력에 등록되어 있지 않다. 이번 확인을 모든 로컬·원격 이력이 동기화되었다는 의미로 해석하거나 곧바로 db push를 실행하지 않는다.

## 입력 검증과 한 번에 적재하기

`scripts/database/manual-observations.mjs`는 상품 상세 화면을 직접 확인해 정리한 입력을 검증하고 SQL을 만든다. 웹사이트 접속이나 DB 인증을 수행하는 수집기는 아니다. 한 번에 최대 20개로 제한하고, 허용한 공식 상품 상세 주소와 상품 번호의 일치, 규격, 가격 범위, 실제 확인 시각을 확인한다.

권리 상태·공개 상태·예시 여부를 입력 자료가 임의로 승인 상태로 지정하게 두지 않는다. 이 단계의 저장 상태를 생성 코드에서 정하고 DB 제약으로 다시 확인한다. 출처 주소를 문자열로 붙여 외부 명령을 실행하지 않으며, SQL에 넣을 자료도 안전한 데이터 표현으로 변환한다.

동일한 관측을 재실행하면 같은 관측을 가리키도록 식별자를 만들고, 기존 사실과 다른데 충돌을 무시하는 처리는 하지 않는다. 상품의 이름·규격이나 기존 관측 사실이 맞지 않으면 전체 적재를 중단한다. 여러 행 중 일부만 저장된 상태가 남지 않도록 하나의 트랜잭션으로 처리한다.

검사는 실제 판매 자료 대신 직접 만든 가상 입력을 사용한다. 실제 값이 바뀌어서 테스트가 실패하거나 실제 자료가 공개 저장소로 섞이는 일을 피하기 위한 선택이다. 로컬 DB 검사는 원래 스키마부터 후속 마이그레이션까지 순서대로 적용한다.

## 확인한 것과 최종 검증 기록

연결 도구의 프로젝트·테이블 조회, 기존 공개 예시 6개, 브라우저의 실제 상세 페이지 3개, CLI의 버전·도움말·변경 파일 생성, 원격 마이그레이션 적용과 이력 조회를 확인했다. 실제 입력은 `.artifacts/catalog/20261112T102259Z/observations.json`에 보관했다.

2026-11-12 19:29:28 KST에 실제 Supabase 적재와 재조회가 성공했다. 검증기는 정규화한 입력과 DB가 반환한 상품·관측의 모든 필드를 비교했으며, 시각 값은 UTC로 통일해 비교했다. 실제 상품 3개·관측 3개가 모두 일치했다. 자체 예시까지 합치면 products 9행·price_observations 9행이었고, 공개 play_catalog는 6행 모두 is_sample=true였다. 공개된 실제 자료는 0행이었다.

생성 SQL에 `SET LOCAL search_path`를 명시한 최종본으로 다시 적용한 뒤에도 전체 9행·9행과 비공개 실제 자료 3개, 공개 예시 6개가 유지되었다. 동일 관측의 재실행이 이력을 늘리지 않는 것을 실제 DB에서도 확인한 결과다. 입력·생성 SQL·원격 검증 결과는 같은 `.artifacts/catalog/20261112T102259Z/` 폴더에 보관하고 Git에서는 제외했다.

로컬 검사 결과는 DB 통합 검사 48개와 입력 검사 15개, 합계 63개 통과였다. 이것은 전체 앱·갤럭시 검사를 대신하지 않는다. 원고를 고정한 뒤 실행하는 이번 실기기 검사의 최종 결과는 같은 커밋의 Android 검증 기록으로 확인한다. 이전 단계의 성공 결과를 이번 변경의 검증으로 대신하지 않는다.

Supabase 보안 점검은 변경 전후 모두 lints가 빈 목록이었다. 성능 점검에는 기존 외래키의 복합 인덱스와 미사용 이력 인덱스에 관한 정보성 항목 2건이 남았다. 상품 수가 적은 현재 단계에서 별도 성능 변경을 섞지 않았으며, 모든 종류의 점검 결과가 비어 있었다고 기록하지 않는다. device:doctor는 준비 완료였지만 이는 전체 화면 검사를 통과했다는 뜻은 아니다.

검증은 다음 층위로 나눈다.

1. 입력 검사: 잘못된 URL·상품 번호·금액·시각·상태와 SQL 문자열 처리.
2. 로컬 SQL 검사: 제약, 역할별 접근, 수동 관측의 공개 차단, 이력 보존, 중복·충돌·부분 적재 방지.
3. 실제 Supabase 확인: 대상 프로젝트에 저장된 행과 확인 시각·출처·비공개 상태를 다시 조회하고 보안 점검 결과 확인.
4. 공개 HTTP와 갤럭시: 기존 예시 6개가 유지되고 비공개 자료가 나오지 않는지 확인하며 장바구니부터 영수증까지 회귀 검사.

코드·실기기 검사가 성공하고 검사 중 파일이 바뀌지 않은 경우에만 기존 자동 실행기가 개발 결과 기록과 로컬 커밋을 만든다. 이 단계의 최종 실기기 결과는 같은 커밋에 포함된 [Android 검증 기록](../verification/latest-android.md)의 시작 HEAD·각 검사 단계·JUnit 결과로 확인한다. 공개 HTTP 검사가 통과해도 비공개 자료의 저장 사실까지 증명하지는 않으므로 관리자 재조회 결과와 구분한다. GitHub 업로드와 태그 생성은 별도 요청에 따라 진행한다.

실제로 실행한 로컬 검사와 이어서 실행하는 전체 검사의 Git Bash 명령은 다음과 같다.

```bash
npm --prefix scripts/database test
cd apps/mobile
npm run verify:device -- --message "feat: SSG 실제 가격 비공개 관측 저장 추가"
```
