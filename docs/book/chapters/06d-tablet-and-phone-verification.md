# 06장 보충. SIM 없는 태블릿과 스마트폰의 검사 조건 구분하기

작업일: 2026-11-16. 시작 HEAD는 `f0b408d`이며 사용자가 GitHub 업로드를 확인했다. 이 커밋은 스마트폰 SM-S948N / Android 17에서 **꼬마 시장 화면 검사** APK의 오프라인 첫 실행·후속 화면 검사·설정 복구를 통과한 기록이다. 당시 실행 ID는 `20261115T175407705Z-9039575e`다.

이번에는 검사 도구를 SIM 없는 태블릿에도 맞추고 SM-X710 / Android 14에서 같은 APK를 검사한다. 앱 소스·DB·API를 바꾸거나 APK를 다시 빌드하지 않는다. 이번 스마트폰 검사는 PC의 모의 회귀 검사이며 새 스마트폰 실기기 결과가 아니다. 이 원고는 최종 전체 검사에 앞서 준비 사실·검사 설계와 첫 실행에서 확인한 문제를 남긴 기록이다.

## 태블릿에서 직접 읽은 상태

준비 점검 `20261116T074122456Z-5df451b9`에서 연결 준비를 확인했다. 다음 값은 설정을 바꾸지 않고 읽었다.

| 항목 | SM-X710에서 확인한 값 |
| --- | --- |
| Android / 현재 사용자 | Android 14 / 사용자 0 |
| 물리 화면 | 1600×2560픽셀 |
| 화면 밀도 | 340, 사용자 지정 override 없음 |
| 글자 배율 | 원문 `1.0` |
| Wi-Fi / 비행기 모드 | 켜짐 / 꺼짐 |
| 원본 `mobile_data` | `1` |
| 기본 데이터 회선 / SIM 상태 | `null` / 빈 값 |
| 정확한 전화 하드웨어 기능 | `feature:android.hardware.telephony` 없음 |
| 이번 APK 설치 여부 | 현재 프로필에 없음 |

전화 기능의 하위 항목인 IMS 관련 기능이 있어도 전화 하드웨어 자체가 있다고 판단하지 않는다. `pm has-feature`는 기능이 없을 때 종료 코드 1을 반환해 기존 명령 성공 처리와 맞지 않았다. `pm list features`에서 정확한 `feature:android.hardware.telephony` 한 줄이 있는지 확인하도록 정리했다.

수정한 네트워크 조회 함수를 실제 태블릿에서 실행한 결과는 `networkMode: wifi-only`, Wi-Fi 켜짐, `mobileDataEnabled: null`, `defaultSubscription: null`, 비행기 모드 꺼짐, 활성 기본 연결 있음, 인터넷 가능 망 1개, USB 역방향 연결 0개였다. `.artifacts/device/tablet-preflight-20261116/classification.json`에 기록했다. 이는 읽기 전용 분류 확인이며 오프라인 검사 성공을 뜻하지 않는다.

## 통신 상태를 두 가지로 구분하는 이유

SIM 없는 태블릿도 원본 `mobile_data`가 `1`일 수 있었다. 이 값을 무조건 모바일 통신 켜짐으로 해석하거나 `0`으로 바꾸지 않는다. 하드웨어 기능·SIM 상태·회선 값을 함께 확인한 뒤 해당 모드의 설정만 다룬다.

| 검사 모드 | 판정 기준 | 변경·복구 방식 |
| --- | --- | --- |
| `wifi-only` | 정확한 전화 하드웨어 기능 없음, SIM 상태 빈 값 또는 ABSENT, 회선 값 null 또는 -1 | Wi-Fi만 잠시 끄고 복구. 원본 모바일 데이터 값 보존. 조회 결과의 모바일 데이터·기본 회선은 null, 모바일 복구는 `not-applicable` |
| `single-sim` | 기존에 지원하던 활성 SIM 한 개의 상태와 회선을 명확히 확인 | 기존처럼 Wi-Fi·모바일 데이터 상태를 boolean으로 기록하고 이번 검사가 바꾼 연결을 복구 |

여러 활성 SIM, 불명확한 응답, 전화 하드웨어는 있지만 SIM이 없는 경우는 이번 지원 범위로 추정하지 않고 중단한다. Wi-Fi 전용 모드도 인터넷 기본 연결·인터넷 가능 망·USB 전달이 모두 없음을 확인하고 검사 중 계속 감시한다. 모바일 데이터 값이 null이라는 이유만으로 오프라인을 인정하지 않는다.

## 첫 전체 실행에서 Expo Go 초기 안내 정리

전체 실행 `20261116T080103448Z-1e61b67d`에서 PC 검사 326개·타입·ESLint·세 플랫폼 번들·공개 HTTP 검사는 통과했다. 이후 내장 예시 선택 검사에서 `catalog-test-marker`를 기다리다 `maestro-loading-choice`가 130,827ms 뒤 실패했다. 앱은 열렸지만 새 기기의 Expo Go 첫 개발 안내와 개발자 메뉴가 앱 화면 계층을 가리고 있었다. 별도로 화면 위에 떠 있던 작은 창은 사용자가 직접 닫았다.

실제 화면에서 Expo Go의 **Continue**와 **Close** 요소를 확인해 초기 안내와 메뉴를 닫았다. 이후 화면 자료에는 현재 실행의 `-loading` 표시가 있는 `catalog-test-marker`와 검사 요청 1회가 정상적으로 노출됐다. 이는 첫 기기의 검사 준비를 마친 확인이며 실패한 시나리오를 통과로 바꾼 결과가 아니다. 앱·검사 YAML·API 코드는 수정하지 않았다.

이 실행은 실패·`commit: null`로 종료했다. APK 설치와 통신·글자 배율·밀도 변경 전에 중단됐고, 화면 유지값 `0 → 7 → 0` 복구를 확인했다. 원본 화면 자료는 `.artifacts/device/20261116T080103448Z-1e61b67d/`의 `expo-onboarding-*.xml`, `expo-ready-after.xml` 등에 보관하며 이미지나 개인 화면 내용을 커밋하지 않는다. 기존 공개 보고서는 변경하지 않았고 같은 전체 검사 명령으로 재실행한다.
