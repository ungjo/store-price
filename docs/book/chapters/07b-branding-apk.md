# 07장 보충. 전용 아이콘·시작 화면과 검사 APK 업데이트

작업일: 2026-11-18. 시작 HEAD는 `bf1663e`이며 사용자가 GitHub 업로드를 확인했다. 코드 `1` 고정 검사 APK의 실제 전체 놀이 PASS는 실행 `20261117T141319521Z-de579384`와 해당 커밋의 보고서에 보존한다.

이번 단계는 정식·검사용 아이콘과 시작 화면을 만들고 **꼬마 시장 검사**의 코드 `2` APK를 기존 태블릿 앱에 업데이트한다. 아래 이미지·설정·도우미 검사 결과와 새 APK의 실제 설치·화면·놀이 결과를 구분한다. 최종 전체 검사 전에 원고를 고정하며 실제 결과는 같은 커밋의 자동 보고서로 확인한다.

## 생성 이미지와 앱 용도를 함께 구분하기

내장 이미지 생성 도구로 사과와 빵을 담은 짙은 초록색 장바구니 그림을 만들었다. 공통 배경은 따뜻한 밝은색 `#FAF8EF`이며, 검사 앱에는 주황색 **검사** 배지를 더했다. 작은 아이콘에서도 장바구니가 드러나고 원형 마스크에서 핵심 그림이 잘리지 않도록 여백을 두는 방향으로 요청했다. 외부 상점의 로고·상품 사진을 가져온 자산이 아니다. 전체 프롬프트와 생성 원본 출처는 [브랜드 자산 기록](../../06-brand-assets.md)에 남긴다.

| 용도 | 파일 접두사 | Android 앱 |
| --- | --- | --- |
| 정식 | `market-` | 꼬마 시장 / `com.ungjo.storeprice` |
| 고정 검사 | `inspection-` | 꼬마 시장 검사 / `com.ungjo.storeprice.inspection` |

각 용도에 `icon.png`, `foreground.png`, `monochrome.png`를 만들어 `assets/brand`에 총 6개 PNG를 저장했다. 모두 1254×1254 정사각형이다. 이미지 검사에서 투명도와 단색 이미지의 색상 조건을 확인했고 72/108 원형 표시 경계 밖의 주요 픽셀(alpha≥128)은 0개였다. 더 보수적인 66/108 안전 원에서는 바구니 하단 모서리 일부가 벗어났다. 이 결과는 원본 자산 검사이며 모든 Android 런처 효과·시작 화면의 표시 결과를 뜻하지 않는다.

정식·검사 설정은 각자의 일반 아이콘, 적응형 전경·단색 레이어를 선택한다. 시작 화면에도 같은 용도의 전경 이미지를 사용해 검사 앱이 정식 앱처럼 보이지 않게 한다. 기존 템플릿의 배경 이미지 레이어는 새 단색 배경을 가리지 않도록 교체했다.

## 시작 화면 설정과 버전 기록

`apps/mobile`에서 SDK에 맞는 패키지를 설치했다.

```bash
npx expo install expo-splash-screen
```

`expo-splash-screen` 58.0.14 설치는 끝났지만 동적 `app.config.js`에 플러그인을 자동 삽입할 수 없다는 안내로 명령이 종료 코드 1을 반환했다. 패키지를 다시 추가하는 대신 동적 설정에 플러그인을 직접 연결했다. `imageWidth: 200`, `resizeMode: contain`, 배경 `#FAF8EF`와 용도별 전경 이미지를 사용한다. 설정을 다시 해석해도 같은 플러그인이 중복되지 않게 했다.

표시 버전은 `1.0.0`을 유지하고 정식·고정 검사 설정의 `versionCode`는 `2`로 올렸다. 매번 새 패키지인 기존 nonce preview는 코드 `1`을 유지한다. 빌드 도우미는 버전을 상수로 가정하지 않고 앱 설정에서 읽어 `inputs.json`에 기록한 뒤 EAS·APK와 대조한다. 기존 schemaVersion 1의 코드 `1` 기록도 읽을 수 있다.

실제 Expo CLI의 세 프로필 해석을 포함한 설정 검사 21개와 타입·ESLint 검사가 통과했다. 설치된 patch 버전은 SDK 호환 범위로 검사하며 특정 patch 문자열 하나와 같아야 한다고 보지 않는다. 아이콘 하위 폴더의 이미지도 빌드 복사본과 소스 지문에 들어가고, 준비 뒤 이미지가 바뀌면 검사를 중단한다.

## 같은 패키지를 업데이트할 근거 만들기

앞 단계의 기본 규칙은 다른 APK가 이미 설치되어 있으면 중단하는 것이었다. 이번에는 사용자가 기존 검사 앱 업데이트를 요청했으므로, 다음 조건을 모두 확인한 경로에서만 `adb install -r`를 사용한다.

1. `--inspection-update-commit bf1663e`가 현재 Git 이력의 조상이며 그 커밋의 고정 검사 APK 보고서가 PASS여야 한다.
2. `--inspection-update-from`으로 지정한 과거 기록의 입력·복사본·EAS 빌드·원본 APK 지문·버전·서명이 보고서와 맞아야 한다.
3. 기기에 설치된 앱이 과거 APK와 같은 SHA-256·버전이어야 하고, 새 APK의 서명도 같으며 버전 코드를 낮추지 않아야 한다.
4. 설치 직전 조건을 다시 확인한 뒤 업데이트하고 새 설치 파일의 지문·버전을 재검사한다.

과거 APK는 현재 소스와 다르므로 별도 `captureHistoricalInspectionApk` API로 검사한다. 당시 복사본·출처·공개 연결 설정·서명 검증은 유지하고, 과거/현재 상태를 별도 WeakMap에 보관해 잘못 섞은 상태를 거부한다. 과거 PASS 지문은 필수 입력이다. 앱 삭제·데이터 초기화 명령은 실행하지 않으며 저장 데이터 전체의 바이트 동일성을 검증했다고 주장하지 않는다.

버전·이미지·과거 APK 검증을 포함한 빌드 도우미 36개와 기존 standalone 도우미 22개, 업데이트 기기 도우미 모의 검사 26개, 과거 PASS 보고서 해석 검사 4개가 통과했다. 과거 지문·서명·버전이 틀린 앱은 거부하고 정확한 업데이트만 허용하는 조건을 확인한 결과이며 실제 설치 성공과는 구분한다.

`node scripts/build/inspection.mjs prepare`로 필요한 파일과 공개 연결 설정만 담은 복사본을 준비하고, 복사본에서 `npm ci --no-audit --no-fund`로 742개 패키지를 약 20초에 설치했다. EAS archive 비교에서 42개 파일이 일치했고 빌드 제출 출력에서 기존 기본 keystore를 재사용함을 확인했다. 앱 원자료나 관리자 키, 기기의 개인 화면은 Git에 포함하지 않는다.

빌드가 `FINISHED`가 된 뒤 APK를 다운로드하고 `.artifacts/build/inspection-79c7e8590dc610f0/provenance.json`에 출처를 저장했다. 실제 `captureInspectionApk` 검사에서 버전 `1.0.0`·코드 `2`, 위 소스 지문과 APK 지문, 기존 APK와 같은 서명 인증서를 확인했다. 이 결과는 파일과 출처의 검증이며 태블릿 설치 완료나 새 아이콘·시작 화면·전체 놀이의 성공을 뜻하지 않는다.

설치형 시작 화면을 먼저 확인하기 위한 사전 업데이트·영상 수집·시각 검토를 마쳤다. 업데이트 당시에는 기존 설치의 지문·버전을 대조했으며, 후속 전체 검사 시작 시 이미 같은 새 APK가 설치돼 있으면 `reused-exact`로 새 파일과의 일치를 검사한다. 이 재사용 결과를 기존 코드 `1`에서 업데이트한 증거로 대신하지 않으며 사전 업데이트 기록과 구분한다.

아래는 사전 설치·시각 확인 뒤 사용할 전체 검사 명령이다. 명령을 기록한 사실만으로 전체 실행 성공을 뜻하지 않는다.

```bash
node scripts/device/verify.mjs --inspection-apk .artifacts/build/inspection-79c7e8590dc610f0/provenance.json --inspection-update-from .artifacts/build/inspection-a8c0f5699d49d2cd/provenance.json --inspection-update-commit bf1663e --message "feat: 꼬마 시장 전용 아이콘과 시작 화면 적용"
```

새 APK의 아이콘·시작 화면 리소스와 실제 기기 표시를 확인하고, 공개 상품·장바구니·계산·퀴즈·영수증·분류 전체 놀이를 같은 APK에서 검사한다. 지연 응답 중 내장 예시 선택은 Expo Go에서 별도로 확인한다. 인터넷 차단·TalkBack 재검사·Google Play 제출·정식 AAB 빌드는 이번 범위에 포함하지 않는다.

Expo Go는 설치형 앱의 시작 화면을 그대로 재현하지 않으므로 시각 확인을 대신할 수 없다. 이 제약과 설정 방법은 [Expo SDK 58 SplashScreen 문서](https://docs.expo.dev/versions/v58.0.0/sdk/splash-screen/)에, APK 내부 리소스 확인 방법은 [Android APK Analyzer 문서](https://developer.android.com/tools/apkanalyzer)에 근거한다.

### 태블릿 연결 준비 중 확인한 상태

태블릿이 `unauthorized`로 표시돼 `adb reconnect offline`을 실행한 뒤에는 ADB 목록이 비어 있었다. Windows의 읽기 전용 `Get-PnpDevice -PresentOnly` 조회에서는 `SAMSUNG Android ADB Interface` 등 관련 장치가 `Status: OK`였다. 저장된 USB 인증 키를 삭제하지 않고 `adb kill-server`, `adb start-server`로 서버를 다시 시작하자 태블릿이 다시 `unauthorized`로 감지됐다. 이후 사용자에게 태블릿의 새 USB 디버깅 허용창 확인을 안내하고 응답을 기다렸다. 드라이버의 정상 인식은 디버깅 승인 완료나 앱 검사 성공과 다르다.

2026-11-17 18:20 UTC / 2026-11-18 03:20 KST에 확인한 EAS 빌드는 `IN_QUEUE`였다. 이 준비 기록 시점에는 새 APK 다운로드·설치·실기기 PASS·자동 커밋이 없었다. 장치 일련번호와 USB 인증 자료는 공개 문서에 기록하지 않는다.

2026-11-17 18:50 UTC / 2026-11-18 03:50 KST 무렵에는 USB 승인이 해결됐다. ADB 상태 `device`, 모델 SM-X710, 잠금 상태 `showing=false`·`inputRestricted=false`를 실제 확인했다. 같은 시점 EAS의 최근 빌드 5개 조회에서 새 빌드는 여전히 `IN_QUEUE`, 이전 4개는 `FINISHED`였다. 연결 준비는 해결됐지만 새 APK 파일은 아직 없었으므로 설치·실기기 검사 성공으로 기록하지 않는다.

이어서 2026-11-17 18:52:39 UTC / 2026-11-18 03:52:39 KST에 기존 설치 앱을 읽기 전용으로 대조했다. `bf1663e`에 커밋된 PASS 보고서와 과거 출처를 `captureHistoricalInspectionApk`로 검증한 뒤, 현재 Android 사용자의 설치 APK SHA-256·버전 `1.0.0`·코드 `1`이 일치함을 확인했다. 과거 APK의 서명 인증서 SHA-256은 `edaa623bf85baefadec02d92e2a40467630d838f20ca6aa1fe9e6594c1c93746`이다. 앱 데이터는 변경하지 않았다. 근거는 새 빌드 폴더의 `previous-installed-preflight.json`과 실행 스크립트 `inspect-previous.mjs`에 보관했다. 새 APK를 기다리는 중의 사전 대조이므로 업데이트나 신규 아이콘·시작 화면의 성공 근거로 사용하지 않는다.

2026-11-17 18:55:58 UTC / 2026-11-18 03:55:58 KST에는 `node scripts/device/verify.mjs --doctor`가 종료 코드 0·`ready`로 통과했다. 실행 기록은 `.artifacts/device/20261117T185558673Z-d581a321/`에 보관한다. 설치 도구·USB 실기기·Git·포트 준비만 확인한 진단이며 화면 검사와 커밋은 실행하지 않았다. 이 시점에도 EAS는 약 한 시간 동안 `IN_QUEUE` 상태였고 새 APK의 다운로드·설치·전체 검사 결과는 남기지 않았다.

### 실제 사전 업데이트와 시각 확인

다음 명령으로 새 APK·과거 PASS 근거·기존 설치를 대조하고 업데이트를 실행했다.

```bash
node .artifacts/build/inspection-79c7e8590dc610f0/inspect-install.mjs --install
```

설치 중 Play Protect 전송 선택 창에서 사용자가 **이번에만 전송**을 선택했고 명령은 종료 코드 0으로 끝났다. `installation-preflight.json`은 `updated-verified`, `installedUpdated: true`, `installedHashVerified: true`로 코드 `1 → 2` 업데이트를 확인했다. `dataPreserved: true`는 삭제·초기화 명령을 사용하지 않았다는 정책 기록이며 저장 자료의 바이트 비교 결과가 아니다. 이 파일의 `nativeUiVerified: false`처럼 설치 무결성 점검과 화면 검증을 구분한다.

APK 내부 리소스 검사에서는 manifest의 icon·roundIcon에서 검사 전경·단색 레이어와 `#FAF8EF` 배경으로 이어지는 연결을 확인했다. `MainActivity`의 `Theme.App.SplashScreen`도 `splashscreen_logo`와 같은 배경을 참조했다. 추출된 런처 192×192, 전경·단색 432×432, 시작 화면 1152×1152 이미지를 원본과 비교하고 검사 배지를 직접 확인했다. 이 근거는 `branding-evidence/summary.json`이며 리사이즈된 이미지의 픽셀 대응을 원본 파일과의 바이트 동일성으로 표현하지 않는다.

실기기 자료는 빌드 폴더의 `branding-20261117T190836842Z-996ab9895aeb8204/`에 모았다. `capture.json`은 수집만 완료한 `capture-only` 기록이고, 별도 `visual-review.json`이 실제 화면을 직접 본 결과다. `system-app-info.png`에서 새 장바구니·주황색 검사 배지·앱 이름을 확인했다. 700ms를 요청한 영상 프레임에는 크림색 배경과 검사 장바구니가, 900ms 요청 프레임에는 시작 화면이 사라지며 목록 로딩으로 전환하는 모습이 보였다. 별도 원본 `after-cold-start.png`에서는 상품 12개·빈 장바구니·놀이돈 10,000원을 확인했다.

### 실패 지점 부분 진단과 스크롤 기준 보완

첫 실패 상태를 유지한 채 `node .artifacts/build/inspection-79c7e8590dc610f0/quiz-probe.mjs`를 실행했다. 목록 위에서 퀴즈로 내려가자 활성화된 정답 확인 버튼이 있었고, 입력돼 있던 0원을 채점해 정답과 거스름돈 0원·남을 돈 9,000원까지 확인했다. 부분 진단 1건은 약 27초에 통과했다. 버튼이 사라졌거나 0원 계산이 실패했다는 증거는 없었으며, 실패한 UP 탐색의 시작 위치를 보완했다.

`apps/mobile/.maestro/solve-quiz.yaml`에서 미채점 안내 검증 뒤에 퀴즈 아래의 “물건을 바꾸면 놀이돈을 다시 골라요.” 안내문까지 DOWN으로 이동하는 단계를 추가했다. 그 뒤 기존처럼 UP으로 확인 버튼을 찾는다. 채점·정답·버튼 사라짐·입력 비활성 검증과 제한 시간은 유지했고, optional 처리로 실패를 숨기지 않았다. 한국어 주석에 스크롤 기준을 추가한 이유를 기록했다.

수정한 공통 흐름을 직접 호출하는 `node .artifacts/build/inspection-79c7e8590dc610f0/quiz-anchor-probe.mjs`에서 0원 문제의 다시 풀기·입력·키보드 닫기·안내문 기준 이동·채점을 3회 연속 통과했다. 두 부분 진단의 JUnit은 빌드 폴더의 `quiz-probe-result.xml`, `quiz-anchor-probe-result.xml`이며 원본 화면과 명령 기록도 별도로 보존했다. 각 진단 후 화면 유지 설정은 원래 값으로 복구했다. 이는 실패 조건의 재현과 보완 확인이며 전체 회귀 검사 성공을 대신하지 않는다.
