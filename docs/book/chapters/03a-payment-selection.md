# 03장 보충. 낼 놀이돈을 하나 고르기

날짜: 2026-11-11

시작 기준: `281a5e9` — 놀이돈 예산과 남을 돈·부족한 돈 표시 구현. 사용자가 직접 커밋하고 GitHub 업로드를 완료했다.

이번 보충 단계의 코드 커밋: 아직 없음. 2026-11-12 사용자가 자동 검사·기록·커밋으로 전환을 요청했으므로, 실기기 자동 검사까지 통과한 뒤 커밋한다.

> 작성 상태: 돈 선택 화면과 쇼핑 상태를 구현했다. 전체 테스트 32개·타입 검사·ESLint·세 플랫폼 번들을 통과했고, 390px·320px 브라우저에서 선택·교체·취소·초기화·비활성 상태를 확인했다. 2026-11-12에 사용자가 갤럭시에서 5,000원 선택 표시·500원 부족 안내·예산 잔액 4,500원 유지를 확인했다. 같은 날 10,000원으로 선택을 교체했을 때 이전 선택 해제·충분하다는 안내·장바구니와 예산 잔액 유지도 확인했다. 선택 취소 후 미선택 안내와 버튼 복원, 장바구니·예산 잔액 유지도 확인했다. 10,000원 선택 후 사과를 한 개 더 담았을 때 총 4개·7,000원·남을 돈 3,000원으로 바뀌고 돈 선택이 초기화되는 것도 확인했다. 총 5개·10,000원에 10,000원을 선택하면 남을 돈 0원과 예산에 딱 맞음·지불할 돈이 충분하다는 안내가 함께 표시되는 것도 확인했다. 당근 한 개 추가로 6개·11,000원·부족한 돈 1,000원이 되면 돈 선택이 초기화되고 금액 버튼이 비활성화되어 10,000원을 눌러도 선택되지 않는 것도 확인했다. 당근을 빼서 예산 안으로 돌아오면 금액 버튼이 다시 활성화되고, 10,000원을 선택해 충분하다는 안내를 볼 수 있는 것도 확인했다. 전체 비우기 후 0개·0원·남을 돈 10,000원으로 돌아오고, 돈 선택이 초기화되며 빈 장바구니에서 금액 선택이 차단되는 것도 확인했다. 새로고침 후 초기화와 iPhone 실기기·화면 읽기는 아직 확인하지 않았다.

## 이번 단계에서 배우는 것

앞 장에서는 “예산 10,000원 안에서 살 수 있을까?”를 살펴봤다. 이번에는 “이 물건값을 내려면 어떤 놀이돈을 고르면 될까?”를 연습한다.

장바구니 아래에 “낼 놀이돈 고르기” 영역을 두고 1,000원·5,000원·10,000원 중 하나를 선택하게 한다. 여러 번 눌러 돈을 쌓는 방식이 아니다. 다른 금액을 누르면 이전 선택을 바꾼다.

선택한 돈이 충분한지까지만 안내한다. 실제 결제 완료와 거스름돈 계산·정답 맞히기는 이번 범위에 포함하지 않는다. 오늘의 놀이돈 예산은 계속 10,000원이며, 돈을 선택했다고 예산이나 예산 잔액을 차감하지 않는다.

## 화면의 안내

금액 버튼에는 색과 “선택됨” 글자를 적용하고, React Native의 선택·비활성 접근성 상태를 코드에 설정했다. 버튼은 각각 조작할 수 있게 두고 결과 영역만 묶어 읽도록 했다. 이 구분의 이유도 한국어 주석으로 남겼다. 화면에는 “물건값”과 “선택한 돈”을 함께 보여주며, 선택 전에는 “아직 안 골랐어요”라고 표시한다.

| 상태 | 안내 |
| --- | --- |
| 장바구니가 비어 있음 | 먼저 물건을 담아 주세요. |
| 장바구니가 예산을 넘음 | 물건을 조금 빼고 놀이돈을 골라요. |
| 돈을 아직 고르지 않음 | 낼 놀이돈을 하나 골라 주세요. |
| 5,500원 물건에 5,000원 선택 | 500원이 더 필요해요. |
| 물건값 이상의 돈 선택 | 이 돈으로 계산할 수 있어요! |

빈 장바구니와 예산 초과 상태에서는 금액 버튼을 비활성화한다. 반면 물건값보다 적은 돈은 고를 수 있게 했다. 부족한 금액을 보고 다시 선택하는 학습을 위해서다.

“선택 취소”는 돈 선택만 지우고 장바구니를 유지한다. 상품을 더 담거나 수량을 줄이거나 품목을 삭제하면 돈을 다시 고르도록 선택을 비운다. 전체 비우기는 장바구니와 선택을 함께 초기화한다.

## 장바구니와 선택을 함께 관리하기

`ShoppingState`에는 기존 장바구니와 `selectedPaymentKrw`를 함께 둔다. 돈을 아직 고르지 않은 상태는 `null`이다.

```typescript
// 물건이 달라졌을 때 돈 선택도 같은 상태 변경 안에서 초기화합니다.
const shopping = {
  cart: { 'sample-apple': 2, 'sample-milk': 1 },
  selectedPaymentKrw: 5000,
};
```

`createShoppingReducer`는 기존 `createCartReducer`를 재사용한다. 상품 수량이나 9개 상한을 새로 구현하지 않고, 기존 장바구니 결과가 실제로 바뀌었을 때만 돈 선택을 비운다. 상한에서 더하기를 눌렀거나 없는 품목을 빼는 것처럼 장바구니 변화가 없는 동작은 기존 선택을 유지한다.

금액 선택에는 다음 조건을 적용한다.

- 등록된 1,000원·5,000원·10,000원 중 하나여야 한다.
- 선택 금액이 오늘의 예산을 넘으면 안 된다.
- 장바구니 합계가 0원보다 크고 예산 이하여야 한다.
- 같은 금액을 다시 고르면 상태를 변경하지 않는다.

안내는 `getPaymentSummary`가 계산한다. `empty` → `over-budget` → `unselected` → `insufficient` → `ready` 순으로 필요한 상태를 판단한다. 먼저 물건을 담거나 예산 안으로 줄여야 하는 상황에서 돈 선택 안내가 먼저 나오는 혼란을 막기 위한 순서다.

부족할 때만 `missingAmountKrw`에 물건값과 선택 금액의 차이를 반환한다. `ready`는 선택한 돈이 충분하다는 뜻이며 결제가 끝났다는 뜻은 아니다. 함수에서 거스름돈을 반환하지 않는다.

핵심 코드에는 적은 돈도 선택할 수 있게 한 이유, 여러 선택을 누적하지 않는 이유, 장바구니 변화와 돈 선택 초기화를 함께 처리하는 이유를 한국어 주석으로 남겼다.

## 실제 검증과 변경 파일

`apps/mobile` 폴더에서 다음 명령을 실제 실행했다. 단독 테스트 **15개 모두 통과**했다.

```bash
node --experimental-strip-types --test src/features/payment/payment.test.ts
```

검사에는 빈 상태·예산 초과 선택 거부, 5,500원에 5,000원을 선택했을 때 500원 부족, 10,000원 선택 시 충분함, 1,000원 물건에 정확히 1,000원 선택, 선택 교체·취소, 장바구니 변화 시 초기화, 9개 상한에서의 선택 유지, 미등록 금액·예산 초과 금액 거부, 이전 상태의 불변성을 포함했다.

검사를 마친 뒤 이 8090 서버만 Ctrl+C로 종료했다. 사용자가 사용하던 휴대전화용 8082 서버는 조작하지 않았다.

| 당근 1개 1,000원에 1,000원 선택 | 지불할 돈이 충분하다는 안내 |
| 같은 상태에서 320 × 720으로 변경 | 돈 선택 유지, 상품 1열, 가로 넘침 없음 |
| 브라우저 새로고침 | 장바구니 0원, 돈 선택 없음, 예산에서 남을 돈 10,000원 |

확인 시점의 브라우저 콘솔에는 경고와 오류가 없었다. 선택됨 글자와 색은 화면으로 확인했다. React Native의 접근성 상태는 코드에 구현했지만 웹 DOM에서 `aria-selected`는 확인되지 않았으며, 실제 화면 읽기 동작을 검증한 것은 아니다. 갤럭시의 사용자 확인 결과는 아래에 별도로 기록하며, iPhone 실기기는 아직 확인하지 않았다.

## 갤럭시 실기기 확인 기록

2026-11-12에 사용자가 사과 2개와 우유 1개를 담은 상태에서 5,000원 버튼에 “선택됨”이 표시되고, “선택한 돈 5,000원”과 “500원이 더 필요해요.” 안내가 보인다고 보고했다. 화면 하단의 남을 돈도 4,500원으로 유지되었다. 상품과 선택은 다음 확인을 위해 그대로 두었다.

이로써 부족한 금액도 선택할 수 있고, 필요한 차액을 안내하면서 예산 잔액은 바꾸지 않는 동작을 갤럭시에서 확인했다.

같은 날 사용자는 10,000원 버튼을 누르자 해당 버튼에 “선택됨”이 표시되고 5,000원 버튼은 “고르기”로 바뀌었다고 보고했다. 선택한 돈은 10,000원이 되었고 “이 돈으로 계산할 수 있어요!” 안내가 표시되었다. 하단은 3개·5,500원과 남을 돈 4,500원을 유지했다. 상품과 선택은 그대로 두었다.

이로써 금액을 누적하지 않고 선택을 교체하며, 충분한 돈을 골랐다는 안내와 장바구니·예산 잔액 유지가 갤럭시에서 확인되었다.

이어서 사용자는 “선택 취소”를 누르면 “아직 안 골랐어요”와 “낼 놀이돈을 하나 골라 주세요.”가 표시된다고 보고했다. 모든 금액 버튼은 “고르기”로 돌아왔고 선택 취소 버튼도 사라졌다. 하단은 3개·5,500원과 남을 돈 4,500원을 유지했다. 상품은 그대로 두고 돈은 다시 고르지 않았다.

이로써 돈 선택만 취소하면서 장바구니와 예산 잔액을 보존하는 동작을 갤럭시에서 확인했다.

이어서 사용자는 10,000원을 다시 선택한 뒤 사과를 한 개 더 담으니 총 4개·7,000원과 남을 돈 3,000원이 표시되었다고 보고했다. “아직 안 골랐어요”와 “낼 놀이돈을 하나 골라 주세요.”가 보였고, 모든 금액 버튼이 “고르기”로 바뀌며 선택 취소 버튼도 사라졌다. 상품은 그대로 두고 돈은 다시 고르지 않았다.

이로써 상품 수량이 바뀌면 새 물건값으로 합계·예산 잔액을 계산하고 기존 돈 선택을 초기화하는 동작을 갤럭시에서 확인했다.

이어서 사용자는 식빵 한 봉을 더 담고 10,000원을 선택하면 총 5개·10,000원과 남을 돈 0원, “놀이돈에 딱 맞아요!”가 표시된다고 보고했다. 10,000원 버튼에는 “선택됨”이 표시되었고 “이 돈으로 계산할 수 있어요!” 안내도 나왔다. 상품과 선택은 그대로 두었다.

이로써 예산에 딱 맞는 장바구니에서 물건값과 같은 금액을 선택할 수 있고, 지불할 돈이 충분하다는 안내가 표시되는 동작을 갤럭시에서 확인했다.

이어서 사용자는 당근 한 개를 더 담으면 총 6개·11,000원과 부족한 돈 1,000원이 표시된다고 보고했다. 돈 선택 영역에는 “아직 안 골랐어요”와 “물건을 조금 빼고 놀이돈을 골라요.”가 보였다. 모든 금액 버튼이 흐려지고 10,000원을 눌러도 선택되지 않았으며, 선택됨 표시와 선택 취소 버튼도 사라졌다. 상품은 그대로 두었다.

이로써 예산 초과 시 기존 돈 선택을 지우고 새 금액 선택도 막는 동작을 갤럭시에서 확인했다.

이어서 사용자는 당근을 빼고 10,000원을 선택하니 총 5개·10,000원과 남을 돈 0원, “놀이돈에 딱 맞아요!”가 표시된다고 보고했다. 금액 버튼이 다시 활성화되었고 10,000원에 “선택됨”이 표시되었다. “선택한 돈 10,000원”과 “이 돈으로 계산할 수 있어요!” 안내도 보였다. 상품과 선택은 그대로 두었다.

이로써 예산 초과 상태에서 물건을 빼 예산 안으로 돌아오면 금액 버튼이 다시 활성화되고 돈을 선택할 수 있는 동작을 갤럭시에서 확인했다.

이어서 사용자는 장바구니를 비우면 0개·0원과 남을 돈 10,000원으로 돌아온다고 보고했다. 빈 장바구니 안내와 “아직 안 골랐어요”, “먼저 물건을 담아 주세요.”가 표시되었다. 금액 버튼은 모두 흐려졌고 10,000원을 눌러도 선택되지 않았으며, 선택됨 표시와 선택 취소 버튼도 사라졌다. 장바구니는 비운 상태로 두었다.

이로써 전체 비우기로 장바구니와 돈 선택을 함께 초기화하고, 빈 장바구니에서는 돈 선택을 막는 동작을 갤럭시에서 확인했다. 다음 수동 확인으로 새로고침 후 초기화를 준비하던 중, 사용자가 반복 검증·기록·커밋의 자동화를 요청했다. 새로고침 수동 확인은 미실시로 남기고, [실기기 검사 자동화](03b-device-automation.md)로 이어 간다.

## 첫 확인을 재현하는 순서

기존 Expo 개발 서버가 켜져 있다면 그 터미널에서 `r`을 눌러 새로고침한다. 사과 2개·우유 1개를 담아 합계를 5,500원으로 만든 뒤 목록 아래 “낼 놀이돈 고르기”에서 5,000원을 누른다.

“물건값 5,500원”, “선택한 돈 5,000원”, “500원이 더 필요해요.”가 보이는지 먼저 확인한다. 이때 예산에서 남을 돈은 여전히 4,500원이어야 한다.

서버가 꺼져 있다면 저장소 루트에서 연 Git Bash에 다음 명령을 입력한다.

```bash
cd apps/mobile
npm start
```

이 순서는 최초 수동 검증을 재현하는 방법이다. 2026-11-12부터는 사용자 요청에 따라 반복 검증과 기록을 자동화하고, 코드·실기기 검사가 모두 성공한 변경을 자동 커밋한다. 태그와 GitHub 업로드는 별도 요청에 따라 진행한다.
