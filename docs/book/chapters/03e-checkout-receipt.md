# 03장 보충. 계산을 마치고 놀이 영수증 받기

날짜: 2026-11-12

시작 커밋: `843ec07` — 거스름돈 맞히기와 자동 검증 추가. 사용자가 GitHub 업로드를 확인한 뒤 이 단계를 시작했다.

## 목표와 놀이 순서

물건을 고르고 거스름돈을 맞히는 연습에 끝맺음을 추가한다. 정답을 맞힌 뒤 **계산 완료**를 누르면 영수증으로 이번 놀이를 마친다.

1. 장바구니에 물건을 담고 충분한 놀이돈을 고른다.
2. 거스름돈의 정답을 입력한다. 딱 맞게 내면 0을 입력한다.
3. 계산 완료를 누르고 산 물건·수량·금액을 확인한다.
4. 낸 놀이돈, 받은 거스름돈, 계산 후 남은 놀이돈을 비교한다.
5. 다시 장보기를 누르면 빈 장바구니와 새 놀이돈 10,000원으로 시작한다.

이번 단계는 한 번의 시장놀이를 완료하는 기능이다. 영수증은 현재 놀이 중 메모리에만 남으며 새 놀이 또는 앱 재시작 때 사라진다. 영수증 이력·저장·공유는 추가하지 않았다. 실제 결제·출금은 일어나지 않는다.

## 계산 완료의 조건

계산 완료 버튼은 항상 돈 고르기 영역 끝에 표시하지만, 현재 장바구니가 예산 안이고 고른 돈이 충분하며 거스름돈을 맞힌 경우에만 활성화한다. 빈 장바구니, 돈 부족, 예산 초과, 미입력·잘못된 입력·오답에서는 완료할 수 없다.

화면의 비활성 표시만 믿지 않는다. reducer는 완료 요청을 처리할 때 현재 물건값과 선택한 돈으로 거스름돈을 다시 구하고, 현재 입력값도 다시 채점한다. 오래된 정답 상태가 남더라도 잘못된 거래를 확정하지 않게 하는 처리다.

## 영수증을 만드는 순간

`receipt.ts`는 상품 ID·이름·단위·단가·수량·품목 합계를 새로운 값으로 복사한다. 전체 수량·총액·지불액·거스름돈·시작 예산·남은 예산도 함께 보관한다. 원래 상품 객체를 참조하지 않아 이후 목록의 이름이나 가격이 바뀌어도 이미 확정한 영수증은 바뀌지 않는다.

`ShoppingState`에 `receipt: Receipt | null`을 추가했다. `complete-checkout`은 영수증 생성과 장바구니·돈 선택·퀴즈 초기화를 한 번의 상태 변경으로 처리한다. 영수증이 있는 동안 중복 완료와 기존 구매·퀴즈 액션은 같은 상태를 반환한다. `start-new-round`만 새 초기 상태로 돌아간다. 진행 중인 장보기에서 잘못 호출된 새 놀이 액션은 물건을 지우지 않는다.

핵심 처리 이유는 한국어 주석으로 남겼다. 날짜·난수·네트워크 없이 원 단위 정수로 계산하므로 같은 입력은 같은 영수증을 만든다.

## 화면과 금액 읽기

`shopping-receipt.tsx`는 상품별 내역, 합계, 낸 돈·거스름돈·남은 돈, 다시 장보기 버튼을 보여 준다. 각 내역만 읽기 단위로 묶고 버튼은 독립적으로 조작할 수 있게 했다. 긴 영수증은 스크롤하며, 행의 글자와 금액은 좁은 화면에서 줄을 바꿀 수 있다.

`App.tsx`는 계산 완료 상태에서 기존 상품 목록·퀴즈·장바구니 하단 요약을 렌더링하지 않는다. 완료 화면에 이전 구매 버튼이 남지 않게 한다. 같은 놀이 화면의 상태를 교체하므로 별도 경로나 화면 이동 라이브러리는 추가하지 않았다.

| 구매 | 낸 놀이돈 | 거스름돈 | 계산 후 남은 놀이돈 |
| --- | --- | --- | --- |
| 사과 2개·우유 1개, 5,500원 | 10,000원 | 4,500원 | 4,500원 |
| 당근 1개, 1,000원 | 1,000원 | 0원 | 9,000원 |
| 당근 1개, 1,000원 | 5,000원 | 4,000원 | 9,000원 |

거스름돈은 낸 금액에서 물건값을 뺀 값이고, 남은 놀이돈은 시작 예산 10,000원에서 물건값을 뺀 값이다. 지불한 지폐 전체를 예산에서 차감하거나 거스름돈을 두 번 더하지 않는다. 다시 장보기는 잔액을 이어 쓰는 기능이 아니라 새 놀이를 시작하는 기능임을 버튼 위에 안내한다.

## 코드 검사와 연결 확인

담당 코어 파일을 대상으로 실제 실행한 Node 검사에서 기존 49개와 새 완료·영수증 검사 16개, 총 **65개가 통과**했다. 새 테스트는 완료 조건 차단, 현재 정답 재검증, 0원, 거스름돈과 잔액 구분, 영수증 복사, 중복 완료, 구매 상태 잠금, 새 놀이와 두 번째 구매를 확인한다.

```bash
cd apps/mobile
node --experimental-strip-types --test src/features/cart/cart.test.ts src/features/budget/budget.test.ts src/features/payment/payment.test.ts src/features/payment/change-quiz.test.ts src/features/payment/receipt.test.ts
npm run typecheck
npm run lint
npm run device:doctor
```

UI 통합 후 타입 검사와 ESLint는 종료 코드 0이었다. device:doctor도 준비 완료로 끝났다. 연결 확인은 휴대전화 화면 검사 성공과 구분한다. package.json의 npm test에도 새 receipt.test.ts를 포함했다.

## 부분 검사와 전체 검사 구분

이전 퀴즈 단계에서는 긴 전체 검사 후반에서 터치 위치 문제를 찾아 여러 번 재실행했다. 이번에는 영수증 구간을 먼저 독립적으로 확인하도록 `--receipt-only`와 `npm run verify:receipt`를 추가했다.

부분 검사도 코드 검사, 새 전용 Expo 서버·실행 ID, 실제 갤럭시와 종료 정리를 사용한다. 다만 전체 회귀 검사를 대신하지 않으므로 **공개 전체 검증 보고서와 커밋을 생성하지 않는다**. 원본 summary.json에 scope를 receipt-only로 기록한다. 이 경계는 코드 리뷰로 확인했다.

```bash
npm run verify:receipt
```

`receipt.yaml`은 비활성 완료 버튼, 세 가지 구매 사례, 내역·금액, 새 장보기, 영수증 상태에서 앱 재시작을 검사한다. 기존 `payment.yaml`의 모든 검사를 보존하고 마지막에 영수증 검사를 연결했다. 둘은 `solve-quiz.yaml`을 재사용하며 세 파일 모두 Maestro 구문 검사를 거친다.

최종 전체 실행과 로컬 커밋:

```bash
npm run verify:device -- --message "feat: 계산 완료와 놀이 영수증 추가"
```

실제 전체 검증 결과는 이 원고와 같은 커밋에 포함되는 [Android 검증 기록](../verification/latest-android.md)의 실행 ID·시작 HEAD·검사 결과로 확인한다. 검사한 파일이 바뀌지 않고 전체 실행이 성공해야 보고서와 명시된 변경 파일을 커밋한다. 부분 검사만 성공했거나 실기기 검사가 실패하면 커밋하지 않는다. GitHub 업로드는 사용자가 별도로 진행한다.

원본 로그·스크린샷·실행 요약은 Git에서 제외한 `.artifacts/device/`에만 보관한다. 이번 갤럭시 자동 검사는 iPhone 실기기·스토어용 빌드·화면 읽기 기능의 수동 검증을 대신하지 않는다.

## 영수증 부분 검사 실제 결과

`npm run verify:receipt` 실행 ID는 `20261111T193802128Z-4355cac0`이다. 코드·구문·세 플랫폼 번들 검사와 영수증 실기기 시나리오가 종료 코드 0으로 통과했다. JUnit은 1 testcase, 실패·오류·건너뜀 0이다.

사과 2개와 우유 1개의 영수증에서 품목별 3,000원·2,500원, 합계 5,500원, 낸 돈 10,000원, 거스름돈·잔액 각 4,500원을 확인했다. 당근 1개를 1,000원으로 계산하는 0원 거스름돈 사례, 5,000원을 내는 거스름돈 4,000원·잔액 9,000원 사례도 통과했다. 새 장보기 후 빈 장바구니·10,000원 복원과 영수증 상태에서 앱 재시작 초기화까지 확인했다. 사과·우유 영수증과 서로 다른 거스름돈·잔액 영수증의 실제 캡처를 열어 읽기와 배치도 확인했다.

실행 요약은 scope=receipt-only, status=passed, commit=null이었다. 검사 후 HEAD는 여전히 `843ec07`이었고 staging은 비어 있었다. 공개 전체 보고서를 HEAD와 비교한 git diff도 변경이 없었다. 화면 유지 설정은 임시 7에서 원래 값 0으로 복원됐다.

이 결과를 기록한 뒤 소스를 고정하고 전체 검사를 실행한다. 부분 성공만으로 전체 장바구니·퀴즈 회귀 검사를 통과한 것으로 기록하거나 커밋하지 않는다.

## 전체 검사에서 발견한 기존 스크롤 문제

첫 전체 실행 `20261111T194414329Z-1127a95b`에서는 코드 검사가 통과했지만, 예산 초과 후 당근 품목을 삭제하려고 위로 스크롤하는 구간에서 멈췄다. `cart-sample-carrot-remove`를 가운데로 옮기는 `scrollUntilVisible`이 30초 안에 끝나지 않았다. 실패 캡처는 화면 맨 위의 상품 소개를 보여 주고 있었으며 장바구니는 검사 전 상태인 6개·11,000원을 유지했다. 삭제 버튼을 누르는 단계에는 도달하지 않았다.

계산 완료 버튼으로 화면 길이가 달라진 뒤 기존 위쪽 탐색이 목표를 지나치는 문제가 드러난 것이다. 새 영수증의 부분 검사 성공을 기존 기능 전체의 성공으로 간주하지 않은 이유이기도 하다. 이 실행은 실패로 기록했고 커밋을 만들지 않았으며 화면 유지 값은 7에서 원래 0으로 복구됐다. 삭제 결과 조건을 유지하면서 버튼을 찾는 동선을 보완하고 해당 구간을 실기기로 먼저 확인한다.

삭제 검사 두 곳을 `내 장바구니` 제목까지 위로 이동한 뒤, 삭제 버튼을 아래 방향으로 찾는 순서로 바꿨다. 두 스크롤 모두 centerElement를 false로 두어 작은 버튼을 가운데로 옮기는 추가 이동을 없앴다. 기존 삭제 결과 검증은 그대로 유지했다.

실기기에서 예산 초과 안내 하단부터 새 경로를 실행해 6개·11,000원에서 당근 삭제 후 5개·10,000원과 돈 선택·퀴즈 초기화를 확인했다. 이어 두 번째 상황을 준비하는 보조 검사에서는 넓은 담기 버튼에 반복 터치를 한 번에 요청해, 첫 담기 뒤 달라진 버튼 위치를 따라가지 못했다. 이 보조 실행의 실패 로그도 보존했다. 실제 앱 수량은 당근 1개였으며 원본 전체 검사에는 이 준비 방식이 없었다.

현재 더하기 버튼을 다시 찾아 나머지 7개를 담고, 당근 8개·8,000원에 10,000원을 선택해 정답 2,000원을 맞힌 뒤 같은 삭제 경로를 확인했다. 이 꼬리 구간은 종료 코드 0과 JUnit 성공으로 끝났고, 삭제 후 0개·0원, 잔액 10,000원, 돈 선택·퀴즈·거스름돈 초기화를 확인했다. 두 확인은 각각 `.artifacts/device/delete-anchor-20261111T195320423Z/`, `.artifacts/device/delete-anchor-tail-20261111T195657435Z/`에 남았다. 새 서버나 USB 포트 연결은 만들지 않았고 임시 화면 유지 설정은 모두 원래 값 0으로 복구했다. 수정한 전체 시나리오로 다시 검증한 뒤에만 커밋한다.
