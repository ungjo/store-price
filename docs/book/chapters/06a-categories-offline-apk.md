# 06장 보충. 예시 12개를 새 APK로 만들고 오프라인에서 확인하기

빌드 작업일: 2026-11-15. 실기기 검사 시각은 자동 보고서에 기록한다. 시작 커밋은 `479f6f5`이며 사용자가 GitHub 업로드를 확인했다. 이 커밋에는 상품 분류와 예시 12개 및 Expo Go 검사가 포함된다. 이번 요청은 그 코드를 새 Android APK로 만들어 설치하고, 실제 인터넷을 끈 상태에서 첫 실행부터 자동으로 검사하는 것이다.

## 이전 앱과 새 앱 구분

앞서 `4fbe035`에서 검사한 **꼬마 시장 검사**는 내장 예시 6개가 포함된 별도 앱이다. 기존 앱을 업데이트하거나 자료를 지우지 않고 보존한다. 이번 앱은 **꼬마 시장 검사 12**로 표시하며, 빌드마다 새 패키지 식별자를 만든다. 이름은 홈 화면에서 구분하기 위한 표시이고, 실제 설치·검사 대상은 고유 패키지와 APK 지문으로 확인한다.

이번에는 상품 가격·계산 규칙·DB 구조·공개 권한을 변경하지 않는다. 자체 예시 12개와 분류를 포함한 현재 소스를 설치형 앱에 반영한다. 실제 가격의 공개·자동 갱신, 마지막 원격 목록의 영구 저장은 후속 범위다.

## 실행 명령

아래는 저장소 루트의 Git Bash 기준이다. 계정 확인과 복사본 준비는 실행했다.

```bash
cd apps/mobile
npx eas-cli@latest whoami
cd ../..
node scripts/build/standalone.mjs prepare
```

준비 명령은 실행할 때마다 새 빌드 표시와 전용 폴더를 만든다. 이번에 준비한 경로는 `.artifacts/build/standalone-c1c1830603cacc67/project`다. 아래 의존성 설치·업로드 검사·빌드 제출·완료 기록 조회·APK 다운로드를 실행했다. Windows에서는 PowerShell 환경 변수 문법과 `npx.cmd`를 사용했으며, 아래는 같은 명령의 Git Bash 표기다.

```bash
cd .artifacts/build/standalone-c1c1830603cacc67/project
npm ci --no-audit --no-fund
EAS_NO_VCS=1 EAS_PROJECT_ROOT="$(pwd -W)" npx eas-cli@latest build:inspect --platform android --profile preview --stage archive --output ../archive-inspection
EAS_NO_VCS=1 EAS_PROJECT_ROOT="$(pwd -W)" npx eas-cli@latest build --platform android --profile preview --message standalone-c1c1830603cacc67 --no-wait
npx eas-cli@latest build:view 9c541054-561e-4aa4-8ec6-6051917b867c --json > ../build.json
cd ../../../..
node scripts/build/standalone.mjs download .artifacts/build/standalone-c1c1830603cacc67
```

다음은 다운로드한 APK를 포함하는 전체 검사 명령이다. 이 명령의 최종 성공은 자동 생성 보고서로 확인한다.

```bash
node scripts/device/verify.mjs --standalone-apk .artifacts/build/standalone-c1c1830603cacc67/provenance.json --message "test: 예시 12개 APK의 오프라인 첫 실행 검증"
```

빌드 기록의 FINISHED 상태를 확인한 뒤 APK를 내려받는다. 업로드 전에 archive 검사 결과의 파일과 복사본을 비교했다. Git Bash의 `pwd -W`로 구한 Windows 절대 경로를 `EAS_PROJECT_ROOT`에 고정해 상위 Git 저장소 전체를 업로드하지 않게 한다. APK와 원시 기록은 Git에서 제외된 `.artifacts`에 둔다.

의존성 설치는 741개 패키지, 약 23초로 완료했다. 업로드 자료는 앱 입력 33개와 생성한 `.easignore` 1개를 합친 34개이며 복사본의 파일·내용과 일치했다. 계정과 프로젝트의 preview 환경에 별도로 등록된 환경 변수가 없다는 응답도 확인했다. 이번 새 패키지의 서명 키는 EAS 클라우드에서 생성했으며 비공개 키를 저장소에 넣지 않았다. 빌드는 2026-11-15 23:16:34 KST에 제출해 23:24:03 KST에 FINISHED가 됐으며 23:26:12 KST에 APK를 내려받았다. 다운로드 파일 크기·지문과 이번 빌드 ID를 위 표에 기록했다.

## 첫 실행과 오프라인을 확인하는 방법

기존 앱을 지우거나 `clearState`로 초기화한 실행을 첫 설치로 간주하지 않는다. 검사기는 현재 Android 프로필에서 새 패키지가 없음을 확인하고, `adb install -R --user <현재 프로필>`로 기존 앱 교체 없이 설치한다. 설치된 파일의 SHA-256과 아직 실행하지 않은 상태를 확인한다.

먼저 코드·DB·공개 HTTP·Expo Go 회귀 검사를 수행한다. 이어 이번 실행기가 만든 개발 서버와 USB 전달 연결을 정리한다. 다른 앱이나 사용자가 별도로 켠 서버를 임의로 종료하지 않는다.

원래 Wi-Fi·모바일 데이터·데이터 회선·비행기 모드 상태를 확인한 뒤 켜져 있던 Wi-Fi와 모바일 데이터만 잠시 끈다. 인터넷 기본 연결·인터넷 가능 망·USB 역방향 연결이 모두 없는지 확인하고, 미실행 상태를 한 번 더 확인한 다음 새 APK를 처음 연다. 첫 화면이 실제 상품 조회 실패로 이어진 뒤 사용자가 선택하는 것과 같은 버튼으로 내장 예시를 연다. 응답을 일부러 실패시키는 개발용 가짜 오류로 대신하지 않는다.

검사 중에도 연결을 감시하며 연결이 다시 생기면 중단한다. 실패·중단 시에도 이번 검사가 바꾼 통신 설정을 먼저 복구한다. 설치된 APK 지문이 같을 때만 이번에 새로 만든 실패 앱을 정리한다. 전체 성공 때는 새 앱을 남기며 이전 6개 예시 앱은 건드리지 않는다.

## 새 APK에서 확인할 내용

기존 분류 검사 흐름을 재사용해 원격 목록·내장 예시·독립 APK의 조건이 달라지지 않게 한다. 호출할 앱과 상품 출처를 명시하고, 새 APK에서는 내장 예시를 사용한다.

1. 인터넷 없는 첫 실행에서 조회 실패·예시 선택·이번 빌드 표시·내장 예시 12개를 확인한다.
2. 기존 사과 2개·우유 1개, 5,500원 합계와 10,000원 지불·4,500원 정답·영수증을 확인한다.
3. 인터넷 차단을 유지한 채 프로세스를 종료하고 다시 열어 예시 선택·12개·빈 놀이 상태를 확인한다.
4. 분류별 과일·채소 6개, 유제품·달걀 4개, 빵·간식 2개와 전체 12개를 확인한다.
5. 서로 다른 분류의 오렌지 1,800원·요구르트 1,200원·크래커 1,500원을 담아 합계 4,500원을 확인한다.
6. 분류를 바꿔도 장바구니·5,000원 선택·퀴즈 답을 유지하고, 거스름돈 500원과 예산에서 남은 돈 5,500원을 영수증에서 구분한다.
7. 다시 장보기에서 빈 장바구니·10,000원·전체 분류로 돌아가는지 확인한다.

별도 `standalone-result.xml`과 화면 자료로 이번 APK의 결과를 남긴다. 마지막에는 통신 설정과 충전 중 화면 유지 값을 원래 상태로 복구하고 확인한다.

## 검증 진행 상태

빌드 입력·업로드 자료 검증, 클라우드 빌드와 APK 다운로드를 완료했다. 이 장 본문은 전체 실기기 실행 전에 고정한 빌드 사실과 검사 설계 기록이다. APK 분석·새 설치·오프라인 실기기의 실제 결과는 자동 보고서에 남긴다. 준비한 시나리오나 이전 APK의 통과 결과를 이번 성공으로 간주하지 않는다.

분류 검사 약 135개 화면 명령을 추가하면서 독립 APK 실행 제한을 300초에서 600초로 늘렸다. 전체 Expo Go 흐름도 앞선 12개 상품 검사에 약 18분이 걸린 점을 반영해 20분에서 25분으로 조정했다. 제한 시간을 없애지 않고 새 검사 분량을 반영한다. 처음 기기 처리 단위 검사에서는 제한 시간을 여전히 300,000ms로 기대하던 가상 실행 검증 때문에 13개 통과·7개 실패가 나왔다. 기대값을 실제 계약인 600,000ms로 수정한 뒤 기기 처리 단위 검사 20개가 모두 통과했다(약 22.3초). 이는 PC 단위 검사 문제이며 새 APK의 실기기 실패가 아니다.

전체 검사가 성공하고 소스·APK·설정 지문이 유지되며 복구까지 확인돼야 자동 보고서와 로컬 커밋을 만든다. 새 결과는 [자동 생성 검증 보고서](../verification/latest-android.md)의 검사 시작 HEAD `479f6f5`, 실행 ID, 새 빌드 표시로 구분한다. 이 문서 작성 시점의 기존 보고서는 앞 단계 결과일 수 있다. GitHub push와 태그는 실행하지 않는다.

iPhone 실기기, Play Store 제출용 AAB·App Store IPA와 스토어 심사는 이번 검사 범위가 아니다.
