## 이번에 확인할 사용 흐름

상품명·규격·가격과 분류 버튼을 읽고 상품을 담을 수 있어야 한다. 글자가 커지면 버튼이나 카드가 필요한 높이를 확보하고, 좁은 화면에서는 가로로 밀려난 동작 없이 필요한 곳까지 스크롤할 수 있어야 한다. 장바구니의 수량·합계와 낼 돈 선택도 같은 기준으로 살핀다.

거스름돈 입력에서는 키보드가 열린 상태에서 입력칸과 **정답 확인**에 접근할 수 있는지가 핵심이다. 입력을 유지한 채 답을 고치고 채점한 뒤, 계산 완료·영수증·다시 장보기까지 이어지는지 확인한다. 글자 크기를 바꾸는 동작 자체와 기존 금액 계산·분류 상태가 서로 섞이지 않아야 한다.

React Native의 `useWindowDimensions`는 창 크기와 글자 배율 변경을 함께 반영한다. 따라서 화면 폭만 고정해 배치하기보다 실제 창과 글자 크기에 맞춰 배치를 정하는 근거로 사용한다. [React Native 창 크기 안내](https://reactnative.dev/docs/usewindowdimensions)

키보드 대응은 화면을 위로 옮겼다는 사실만으로 끝내지 않는다. 플랫폼별 키보드 동작과 스크롤 높이·터치 전달까지 실제 기기에서 확인해야 한다. [KeyboardAvoidingView](https://reactnative.dev/docs/keyboardavoidingview) · [ScrollView](https://reactnative.dev/docs/scrollview)

## 화면을 바꾸는 기준과 구현

기존 상품 목록은 화면 폭이 380dp보다 작거나 글자 배율이 1.2보다 크면 한 열로 표시했다. 분류·장바구니·거스름돈 입력에도 같은 기준을 적용한다. OS에서 고른 글자 크기를 줄여 맞추지 않고, 요소를 아래로 배치하고 스크롤할 공간을 확보한다.

```typescript
const { width, fontScale } = useWindowDimensions();
// 큰 글자와 좁은 화면에서는 가로로 나란히 놓던 내용을 세로로 펼칩니다.
const compactLayout = width < 380 || fontScale > 1.2;
```

`App.tsx`에서는 좁은 배치의 장바구니 상품 정보와 수량 버튼을 세로로 놓는다. 합계도 장바구니 뒤의 스크롤 영역으로 옮겨, 높아진 고정 합계가 상품과 입력 공간을 가리지 않게 한다. 일반 배치에서는 키보드가 열릴 때 고정 합계를 잠시 숨긴다. 두 위치의 합계는 같은 계산 결과를 사용하고 정답 전 잔액 가리기 규칙도 유지한다. 키보드 표시 여부는 화면 배치만 바꾸며 장바구니나 답을 지우지 않는다.

`category-selector.tsx`는 같은 조건에서 분류 버튼을 한 열로 펼친다. `change-quiz.tsx`는 입력칸과 ‘원’을 한 줄로 묶고 **정답 확인**을 다음 줄 전체 폭에 배치한다. 버튼의 고정 폭과 강제 줄바꿈을 없애고, 입력칸의 좌우 여백을 줄여 다섯 자리 답을 입력할 공간을 확보한다. 기존 정답 계산·입력 길이 제한·접근성 이름·자동 검사용 식별자는 유지한다.

목록을 스크롤하는 동작만으로 키보드를 자동으로 닫지 않도록 설정한다. 키보드를 열어 둔 채 확인 버튼까지 이동한 뒤 첫 터치로 채점되는지는 실제 키보드 표시 상태와 화면 위치를 함께 검사한다. 구현 변경만으로 이 동작을 통과했다고 판단하지 않는다.

실기기에서 큰 글자 조건을 적용하자 Android가 입력칸만 키보드 위로 올리고 바로 아래 확인 버튼은 가리는 문제가 드러났다. 입력칸과 버튼을 묶은 영역을 `onAnswerFocus`로 상위 화면에 전달하고, `measureInWindow`로 그 영역과 실제 목록 표시 영역을 측정하도록 보완했다. 아래쪽이 넘치면 `FlatList.scrollToOffset`으로 필요한 만큼 스크롤해 버튼까지 함께 올린다. 키보드 표시·목록 크기 변경 때 다시 계산하며, 입력 포커스 해제·화면 정리 때 참조와 예약된 측정을 정리한다. React Native 0.88의 View 참조는 `ComponentRef<typeof View>`로 선언했다.

코드 검토에서는 `Keyboard.isVisible` 메서드를 상태 초기화 함수로 직접 넘기면 호출 대상인 `this`를 잃을 수 있다는 점을 발견했다. `useState(() => Keyboard.isVisible())`로 감싸 원래 객체의 메서드로 호출하게 고쳤다. 이는 기기에서 발생한 오류를 재현한 기록이 아니라 실행 전 코드 검토에서 수정한 내용이다.

## 조건별 자동 검사

물리 해상도는 그대로 두고 글자 배율과 화면 밀도를 바꿔 다음 세 조건을 만든다. 이 기기의 기존 사용자 밀도는 560이며, 720을 적용하면 1440픽셀 폭이 320dp로 환산된다. 작은 휴대전화를 새로 연결한 검사가 아니라 같은 갤럭시에서 앱에 주어지는 폭을 좁힌 검사다.

| 조건 | 글자 배율 | 화면 밀도 | 환산 폭 |
| --- | --- | --- | --- |
| 기본 | 1.0 | 560 | 약 411dp |
| 큰 글자 | 1.5 | 560 | 약 411dp |
| 좁은 화면과 큰 글자 | 1.5 | 720 | 320dp |

각 조건에서 같은 상품·계산 흐름을 사용해 배치의 차이를 확인한다. 크래커 1개 1,500원을 담고 5,000원을 내면 정답은 3,500원, 놀이돈 잔액은 8,500원이다.

1. `readability-open.yaml`은 분류·상품·장바구니를 거쳐 답 `12345`를 입력하고 키보드를 열어 둔 채 끝낸다. Android가 보고한 실제 키보드 영역과 앱 화면 계층을 읽어 입력칸·확인 버튼 전체가 키보드 위에 있고 서로 겹치지 않는지 확인한다. 입력값과 포커스도 검사한다.
2. `readability-correct.yaml`은 **정답 확인**을 한 번 눌러 오답 안내가 나오는지 확인한 뒤 `3500`으로 고친다. 다시 키보드를 열어 둔 상태에서 같은 영역·입력값 검사를 한다.
3. `readability-finish.yaml`은 확인 버튼을 한 번 눌러 정답 처리한 뒤 영수증의 합계·낸 돈·거스름돈·잔액과 새 놀이 초기화를 확인한다.

한 요소의 중심 좌표만 보이거나 입력칸에 포커스만 있다는 이유로 키보드 검사를 통과시키지 않는다. 실제 키보드가 열렸다는 Android 상태와 영역, 입력칸·버튼 전체의 위치가 함께 맞아야 한다. 스크린샷과 원본 화면 자료는 Git에서 제외하는 실행 폴더에 남긴다.

## 실행 명령과 설정 복구

저장소 루트의 Git Bash에서 화면 사용성만 진단할 때는 다음 명령을 사용한다.

```bash
node scripts/device/verify.mjs --readability-only
```

이 명령도 코드 검사를 수행하지만 기존 장바구니·계산 전체 시나리오는 생략한다. 부분 진단은 자동 커밋하거나 전체 검증 보고서를 덮어쓰지 않는다. 구현을 고친 뒤 기존 기능과 새 화면 조건을 함께 검사하고 자동 커밋하려면 다음 명령을 사용한다.

```bash
node scripts/device/verify.mjs --readability --message "feat: 큰 글자와 좁은 화면의 계산 사용성 개선"
```

`display-settings.mjs`는 쓰기 전에 현재 Android 프로필·글자 배율의 원래 문자열·물리/사용자 지정 밀도·화면 크기를 기록한다. 검사 중에는 적용값을 다시 읽어 확인하고 종료할 때 원래 값으로 복구한다. 기존 사용자 밀도 560을 공장 기본 밀도 600으로 초기화하지 않는다. 중간 오류가 나도 바꾼 항목의 복구를 시도하며, 다른 사용자 변경이나 프로필 전환을 발견하면 그 값을 덮어쓰지 않고 검사를 중단한다.

## 세 차례의 실기기 부분 진단과 수정

다음 실행은 모두 `node scripts/device/verify.mjs --readability-only`로 진행했다. 각 실행의 원본 자료는 `.artifacts/device/<실행 ID>/`에 보관하며 Git에는 올리지 않는다. 실행 ID의 날짜는 UTC라서 `20261115`로 시작하지만 세 실행 모두 한국 시각으로는 2026-11-16이다. 세 실행의 전체 상태는 모두 실패이며, 통과한 구간과 실패 원인을 구분한다.

| 실행 ID | 관측 결과 | 후속 조치 |
| --- | --- | --- |
| `20261115T152658113Z-badb8a33` | 기본 조건의 첫 시나리오 35개 명령 통과 후 키보드 영역 읽기 실패 | Android 17의 `visibleFrame` 출력 형식 허용, 회귀 검사 1개 추가 |

첫 실행은 앱의 키보드 배치 실패가 아니었다. Android 17이 보고하는 IME `frame` 뒤에 `visibleFrame` 항목이 있어 검사기가 읽지 못했다. 형식을 허용한 뒤 저장된 자료를 다시 분석했을 때 입력칸·확인 버튼의 아래쪽 1349픽셀이 키보드 위쪽 1798픽셀보다 위에 있었다. 실제 키보드가 보인다는 조건과 요소 전체 영역 검사는 그대로 유지했다.

두 번째 실행에서는 큰 글자에서 입력칸만 자동으로 올라오고 확인 버튼은 가려지는 실제 배치 문제를 확인했다. 앞 절의 영역 측정·스크롤 보완을 적용한 뒤 세 번째 실행에서는 기본과 큰 글자 각각의 세 시나리오 및 두 번의 키보드 실측을 통과했다.

세 번째 실행의 320dp·글자 배율 1.5 조건도 입력 준비·오답 수정·두 번의 키보드 실측을 통과했다. 이어 한 번의 터치로 정답을 처리하고 영수증까지 표시했다. 좁은 화면의 분류·상품·장바구니·키보드 및 영수증 스크린샷을 살펴 글자와 금액 표시를 확인했다. 다만 새 놀이에서 전체 12개 상품을 지나 빈 장바구니까지 이동하는 검사는 기존 30초 제한 안에 끝나지 않았다. 실패 스크린샷은 9·10번째 상품인 오이·요구르트까지 이동한 상태였고 로그는 `No visible element found: id: cart-empty`를 기록했다. 이 구간만 90초로 늘렸고, 다음 전체 실행에서 새 놀이까지 통과했다.

세 실행 모두 종료 후 원래 글자 배율 문자열 `1.0`, 사용자 밀도 `560`, 충전 중 화면 유지값 `0`으로 복구됐음을 다시 읽어 확인했다. 각 `summary.json`에는 `readability-only`, `failed`, `commit: null`과 복구 확인 결과가 남아 있다. 부분 진단은 기존 전체 보고서를 덮어쓰지 않았고 커밋도 만들지 않았다.

## 첫 전체 검사와 기존 퀴즈 검사 보완

`--readability --message "feat: 큰 글자와 좁은 화면의 계산 사용성 개선"`을 사용한 전체 실행 `20261115T155535716Z-f7d95a90`에서는 코드 검사 299개·세 플랫폼 번들·조회 중 내장 예시 선택이 통과했다. 기본·큰 글자·좁은 화면 모두 세 시나리오와 각 두 번의 키보드 실측을 통과했다. 90초로 조정한 좁은 화면의 빈 장바구니 확인도 성공했고, 글자 배율·밀도를 원래 값으로 복구했다.

이어 기존 전체 놀이 검사에서 `solve-quiz.yaml`이 키보드가 열린 상태로 `cart-summary`를 찾으려다 실패했다. 오답을 지운 뒤 공통 검사를 호출하는 흐름이었으며, 일반 배치에서 키보드가 열리면 고정 합계를 숨기는 새 정책과 기존 검사의 전제가 맞지 않았다. 처음에는 공통 검사 시작에 `hideKeyboard`를 추가했으나 다음 실행에서 닫힌 키보드에도 호출되는 문제가 드러나 적용 위치를 다시 조정했다. 열린 키보드에서 첫 터치로 채점하는 동작과 실제 영역 검사는 별도의 화면 사용성 시나리오에서 계속 확인한다.

이 전체 실행의 최종 상태도 실패이고 `commit: null`이다. 종료 시 화면 유지값 `0` 복구까지 확인했다.

다음 전체 실행 `20261115T161427287Z-cbc8b4e2`는 내장 예시 선택 검사의 초반에 실패했다. 이미 키보드가 닫힌 호출에서도 공통 `hideKeyboard`가 실행돼 Android 뒤로 가기처럼 작동했고, 실패 스크린샷에서 Expo Go 홈으로 이동한 것을 확인했다. `solve-quiz.yaml`은 이전 상태로 복원하고, 바로 앞에서 입력칸을 누르고 답을 지워 키보드가 열린 것이 확실한 `payment.yaml`의 두 구간과 `receipt.yaml`의 한 구간에만 닫기를 추가했다. 앱 코드는 더 바꾸지 않았다. 이 실행은 화면 사용성 단계 전에 끝나 글자 배율·밀도를 변경하지 않았고, 화면 유지값 `0` 복구와 커밋 없음도 확인했다. 답을 지운 세 구간에 닫기를 적용한 최종 상태로 전체 검사를 다시 진행한다.

## 검사 기록의 구분

이 장은 기기 원래 상태를 읽은 결과, 구현한 변경, PC에서 실행한 검사와 실제 갤럭시 검사를 구분해 남긴다. 큰 글자·작은 화면 조건을 만들기 위해 임시 설정을 적용한다면 기존 값과 적용값·복구 결과를 함께 기록한다. 기본값으로 일괄 초기화해 사용자의 기존 설정을 지우지 않는다.

최종 전체 재검사 전에는 구현·검사 설계와 앞서 완료한 확인 결과를 원고에 고정한다. 최종 실행 ID·전체 단계 결과·설정 복구는 [자동 검증 보고서](../verification/latest-android.md)에 남긴다. 검사 시작 HEAD가 `125d852`인지 확인해 앞 단계 보고서와 구분한다. 앞 단계 APK 결과나 개별 구간의 통과만으로 이번 전체 실기기 검증 완료를 뜻하지 않는다.

## 범위

이번 단계는 Expo Go에서 현재 앱 화면을 점검하고 개선하는 작업이다. 상품 DB·가격·공개 권한을 바꾸거나 새 APK를 빌드하는 요청은 포함되지 않는다. 이미 설치한 **꼬마 시장 검사 12**에는 `125d852` 단계의 코드가 들어 있으므로 이후 화면 개선이 저절로 반영되지는 않는다.

한 갤럭시에서 화면 조건을 바꾼 결과를 모든 작은 휴대전화나 iPhone의 결과로 일반화하지 않는다. 화면 읽기 도구의 전체 동선, 실제 초등학생과의 사용성 관찰, iPhone 실기기와 스토어 제출 검증은 별도로 확인해야 한다. 모든 필수 검사를 통과하고 검사한 파일이 유지된 경우에만 원고·보고서와 변경 코드를 자동 커밋하며, GitHub 업로드는 별도 요청에 따라 진행한다.
