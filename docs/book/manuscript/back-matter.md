# 부록 A 자주 쓰는 명령어

명령은 Windows의 Git Bash 기준이다. 명령보다 먼저 현재 폴더를 확인한다. 아래에서 **저장소 루트**는 현재 실습 폴더 `work/chNN`, **앱 폴더**는 그 아래 `apps/mobile`을 뜻한다. `NN`은 실제 장 번호로 바꿔 읽는다.

## A.1 폴더와 파일

| 할 일 | 명령 | 기대하는 확인 |
| --- | --- | --- |
| 현재 위치 | `pwd` | 지금 작업할 폴더인지 |
| 파일 목록 | `ls` | 필요한 파일이 있는지 |
| 앱 폴더로 이동 | `cd apps/mobile` | 저장소 루트에서 실행 |
| 앱 폴더에서 루트로 | `cd ../..` | 두 단계 위로 이동 |
| 새 장의 참고본 준비 | `node start.mjs 17` | `kit`에서 실행, 출력 경로 확인 |
| 이름에 공백이 있는 폴더 | `cd "내 실습 폴더"` | 큰따옴표로 경로 묶기 |
| 실행 중인 서버 종료 | Ctrl+C | 같은 터미널이 입력 가능한 상태 |

`cd`로 이동해도 VS Code 탐색기에 열린 폴더가 자동으로 바뀌지는 않는다. 탐색기에서 다른 장의 파일을 고치고 터미널에서 이전 장을 실행하는 일이 없도록 창 제목·탐색기·`pwd`를 함께 확인한다.

### Git Bash와 VS Code의 도움말 읽기

Git Bash에서 `help`를 입력하면 셸의 내장 명령 목록이 나온다. `help cd`로 폴더를 옮기는 방법을 읽어 보자. Git에서는 `git help`로 자주 쓰는 명령을, `git status -h`로 상태 조회 옵션을 확인한다.

VS Code에서 **터미널 → 새 터미널**을 열고 `code --help`를 입력하면 편집기를 실행할 때 줄 수 있는 옵션이 나온다. `code`를 찾을 수 없다는 메시지가 떠도, 실습 명령은 VS Code에서 **F1**을 눌러 열 수 있다. [부록 C.1의 실습 도움말](#appC-s1)에서 원하는 장을 고른다.

Git으로 실습을 기록하는 순서는 `git status`로 변경 확인 → `git add`로 파일 선택 → `git commit`으로 로컬 기록 → `git show`로 내용 확인 → `git push`로 업로드다. [부록 C.6에서 사과 가격 한 줄로 따라 한다](#appC-s6).

## A.2 패키지와 앱 실행

| 위치 | 목적 | 명령 |
| --- | --- | --- |
| 아무 폴더 | Node 확인 | `node -v` |
| 아무 폴더 | npm 확인 | `npm -v` |
| 앱 폴더 | 잠금 파일 기준 패키지 설치 | `npm ci` |
| 앱 폴더 | Expo 개발 서버 | `npm start` |
| 앱 폴더 | 웹 미리보기 | `npm run web` |
| 앱 폴더 | 다른 포트로 서버 | `npm start -- --port 8082` |
| 앱 폴더 | Expo 호환 패키지 추가 | `npx expo install 패키지명` |
| 앱 폴더 | 설치 버전 확인 | `npm ls expo react react-native` |
| 앱 폴더 | 최종 앱 설정 읽기 | `npx expo config --type public` |

`npm ci`는 현재 잠금 파일을 기준으로 의존성을 다시 설치한다. 소스나 잠금 파일을 바꾼 뒤 설치 상태를 맞출 때 사용한다. 개발 서버를 켤 때마다 반복할 필요는 없다.

`npx expo install 패키지명`의 ‘패키지명’은 설명용이다. 예를 들어 시작 화면을 추가할 때는 `npx expo install expo-splash-screen`을 사용한다. 라이브러리 하나를 넣은 뒤 `package.json`과 `package-lock.json`이 함께 바뀌었는지 본다.

## A.4 USB와 기기 자동 검사

| 목적 | 명령 | 확인할 것 |
| --- | --- | --- |
| ADB 버전 | `adb version` | 실행 경로와 버전 |
| 연결 목록 | `adb devices -l` | 대상 기기의 `device` 상태 |
| USB 한 대 지정 | `adb -d shell getprop ro.product.model` | 본인 기기 모델 |
| Android 버전 | `adb -d shell getprop ro.build.version.release` | 검사 기록에 쓸 버전 |
| Maestro 버전 | `maestro --version` | 프로젝트 검증 기준 2.12.1 |
| YAML 구문 검사 | `maestro check-syntax .artifacts/book-checks/one-apple.yaml` | 실제 기기 조작 전 오류 확인 |
| 준비 진단 | `node scripts/device/verify.mjs --doctor` | 도구·기기·Git 준비 |
| 커밋 없는 전체 검사 | `node scripts/device/verify.mjs --no-commit` | 결과와 설정 복구 |
| 앱 폴더에서 같은 검사 | `npm run verify:device:check` | 같은 비커밋 경로 |
| 영수증 부분 검사 | `node scripts/device/verify.mjs --receipt-only` | 전체 검사와 범위 구분 |

이 표의 `verify.mjs` 명령은 저장소 루트에서 실행한다. 코드가 들어 있는 같은 파일을 앱 폴더에서 직접 실행하면 경로가 맞지 않는다. npm 스크립트가 있는 경우 앱 폴더에서 해당 스크립트를 사용할 수 있다.

## A.5 APK 빌드와 설치

계정·프로젝트·공개 환경 변수·개인 패키지를 먼저 준비한 뒤 19장의 순서로 실행한다.

| 위치 | 목적 | 명령 |
| --- | --- | --- |
| 앱 폴더 | EAS 버전 | `npx eas-cli@latest --version` |
| 앱 폴더 | 본인 로그인 | `npx eas-cli@latest login` |
| 앱 폴더 | 계정 확인 | `npx eas-cli@latest whoami` |
| 앱 폴더 | 프로젝트 연결 | `npx eas-cli@latest init` |
| 앱 폴더 | 프로젝트 확인 | `npx eas-cli@latest project:info` |
| 앱 폴더 | 검사 APK 빌드 | `npx eas-cli@latest build --platform android --profile inspection` |
| 앱 폴더 | 최근 검사 빌드 | `npx eas-cli@latest build:list --platform android --build-profile inspection --limit 3` |
| 파일이 있는 경로 | 파일 지문 | `sha256sum "market-inspection-v1.apk"` |

설치는 다운로드한 파일과 기존 설치 여부를 확인한 다음 한다.

```bash
adb -d install --user "$BOOK_ANDROID_USER" "$BOOK_APK"
```

업데이트는 같은 본인 패키지·서명이고 버전 코드를 올린 새 APK일 때 한다.

```bash
adb -d install -r --user "$BOOK_ANDROID_USER" "$BOOK_APK_V2"
```

변수는 19.6절과 19.8절에서 실제 값으로 준비한다. 새 터미널에는 이전 터미널의 변수가 없을 수 있다. 빈 값인 채 표의 설치 명령부터 실행하지 않는다.

# 부록 B 자주 만나는 오류

오류 문장을 복사할 때 계정·토큰·기기 번호는 제외한다. ‘안 된다’는 설명보다 **어디에서, 무슨 명령을 실행했고, 어느 문장이 나왔는지**가 원인을 좁히는 데 도움이 된다.

## B.1 설치와 실행

| 증상 | 확인 순서 | 해결 후 확인 |
| --- | --- | --- |
| `node`·`npm`을 찾지 못함 | 설치 여부 → 새 터미널 → 실행 경로 | `node -v`, `npm -v` |
| PowerShell에서 npm 실행 정책 오류 | 터미널 종류 확인 | Git Bash에서 같은 npm 명령 |
| `package.json`을 찾지 못함 | `pwd`·`ls` → 앱 폴더 이동 | `npm ci` |
| `npm ci` 실패 | 첫 오류 → package와 lock의 짝 → Node 버전 | 같은 단계 파일로 재설치 |
| 모듈을 못 찾음 | 철자·대소문자 → 상대 경로 → 실제 파일 | 타입 검사와 실행 |
| 화면이 이전 코드임 | VS Code 폴더와 터미널 폴더 → 저장 여부 → 열린 Expo 프로젝트 | 바꾼 문구 확인 |
| 포트 사용 중 | 내가 켜 둔 터미널 확인 | 해당 서버 종료 또는 새 포트 |

개발 서버 문제가 생겼다고 모든 Node 프로세스를 한꺼번에 종료하지 않는다. 자신이 시작한 서버 터미널을 찾아 종료한다. 다른 작업의 서버까지 끄면 새 문제를 만들 수 있다.

## B.2 Expo Go 연결

**QR을 읽었는데 앱이 열리지 않는다**

1. PC와 기기가 같은 네트워크인지 확인한다.
2. 게스트 Wi-Fi가 기기 간 통신을 막는지 확인한다.
3. VPN이나 회사 방화벽의 연결 제한을 확인한다.
4. 터미널의 서버가 아직 실행 중인지 확인한다.
5. 앱을 다시 열었을 때 나오는 정확한 오류를 읽는다.

USB 역방향 연결을 사용하는 자동 검사와 일반 Wi-Fi QR 연결은 준비 조건이 다르다. 일반 Wi-Fi 실습에서 서버를 `--localhost`로만 열면 기기가 PC에 접근하지 못할 수 있다.

**SDK 버전이 맞지 않는다는 안내가 나온다**

1. `package.json`의 Expo 주 버전을 확인한다.
2. 기기의 Expo Go가 그 SDK를 지원하는지 공식 안내에서 확인한다.
3. 책의 잠금 파일과 설치된 패키지가 맞는지 확인한다.
4. 버전을 조정했다면 앱 코드·패키지·검사를 함께 확인한다.

React Native만 따로 최신으로 바꾸거나 에러 메시지를 무시한 채 다른 SDK의 코드를 섞지 않는다. 이 책의 참고 앱은 SDK 58 기준이다. 사용 시점의 설치 가능한 Expo Go는 [공식 Expo Go 페이지](https://expo.dev/go)에서 확인한다.

## B.3 화면과 계산

| 증상 | 확인할 위치 |
| --- | --- |
| 가격이 문자열처럼 이어짐 | 상품 타입과 숫자 값 |
| 수량을 줄여도 합계가 그대로 | 상태 변경과 합계 계산의 입력 |
| 분류를 바꾸자 장바구니가 사라짐 | 필터 상태와 장바구니 상태의 분리 |
| 0원을 입력했는데 빈 답으로 처리 | 빈 문자열과 숫자 0을 구분하는 조건 |
| 정답 뒤 물건을 바꿔도 완료 가능 | 장바구니 변경 시 선택·퀴즈 초기화 |
| 영수증 품목이 달라짐 | 완료 순간의 상품·가격 복사 |
| 큰 글자에서 확인 버튼이 가림 | 실제 글자 배율·스크롤·키보드 영역 |
| TalkBack이 같은 안내를 두 번 읽음 | 이름·상태·live 알림의 중복 |

화면 문제를 확인할 때는 ‘잘 보인다’보다 조건을 적는다. 예를 들어 ‘기본 글자 크기에서는 보이지만 글자 배율을 키우면 숫자 키보드 아래에 정답 확인 버튼이 가려진다’라고 쓰면 재현할 수 있다.

## B.4 데이터와 환경 변수

**PC에서는 상품이 보이는데 APK에서는 연결 설정이 없다고 한다**

`.env.local`은 PC 개발 환경의 파일이다. EAS 빌드는 선택한 환경 변수 묶음을 사용한다. `inspection` 프로필이 선택하는 환경이 `preview`인지, 본인 공개 URL과 publishable 키가 그 환경에 등록되어 있는지 확인한다. APK 안에 들어가는 값이 바뀌면 새 빌드가 필요하다.

**공개 키를 넣었는데 비공개 자료까지 보여야 한다고 생각했다**

공개 키는 모든 데이터를 읽는 관리자 열쇠가 아니다. 앱에 보일 범위는 DB의 공개 뷰·권한·RLS로 정한다. 비공개 관측 자료는 일반 놀이 목록에 나오지 않는 것이 이 프로젝트의 의도다. 문제 해결을 위해 앱에 서버용 비밀 키를 넣지 않는다.

**연결 실패 후 내장 예시로 시작했는데 서버 가격이 반영되지 않는다**

한 놀이 중에는 선택한 상품 목록을 유지한다. 늦게 온 원격 응답으로 장바구니의 가격을 바꾸지 않기 위한 동작이다. 실제로 사용한 출처 문구를 읽고 새 놀이·재시도의 경로를 구분한다.

## B.5 기기 자동 검사

| 메시지 또는 실패 | 먼저 할 일 |
| --- | --- |
| `unauthorized` | 기기 잠금 해제 후 USB 허용 |
| `offline` | 케이블 재연결 후 상태 다시 읽기 |
| 기기 여러 대 | 한 대만 연결하거나 실제 번호 지정 |
| JDK 21 요구 | `JAVA_HOME`과 `java -version` 대조 |
| Maestro 버전 요구 | 2.12.1 실행 경로 확인 |
| Git HEAD가 없음 | 새 참고본의 최초 커밋 준비 |
| attached branch 요구 | 별도 실습 복사본에서 브랜치 만들기 |
| existing staged changes | 본인 staging을 검토; 도구가 대신 없애도록 하지 않기 |
| allowlist 밖 변경 | 표시된 파일을 읽고 예상한 변경인지 확인 |
| 검사 중 파일 변경 | 변경을 마친 뒤 같은 파일로 재검사 |
| testID 탐색 실패 | 실패 PNG·YAML·현재 컴포넌트의 ID 대조 |
| 전체 실행 실패인데 과거 PASS 보임 | 이번 실행 ID의 `summary.json` 읽기 |

`--no-commit`도 파일과 Git 상태를 확인한다. 보호 조건을 건너뛰는 옵션으로 이해하지 않는다. 새 독자 시나리오는 `.artifacts/book-checks`에 두면 기존 저장소의 커밋 대상과 섞이지 않는다.

## B.6 APK와 업데이트

| 증상 | 원인 후보 | 조치 |
| --- | --- | --- |
| 프로젝트 권한 없음 | 저자 projectId 또는 다른 계정 | 본인 owner·slug·projectId 연결 |
| 이미지 파일 없음 | 대소문자·업로드 제외 규칙 | archive에서 PNG 확인 |
| APK 대신 AAB | 잘못된 빌드 프로필 | `inspection`·`apk` 확인 |
| 설치 제한·대기 | 기기 확인창 또는 관리 정책 | 기기의 내용을 읽고 본인이 선택 |
| 업데이트 서명 불일치 | 다른 프로젝트·서명 키 | 기존 앱 보존 후 첫 빌드와 비교 |
| 버전 낮춤 오류 | 기존보다 낮은 versionCode | 더 높은 코드로 새 빌드 |
| 설치했지만 옛 아이콘 | 다른 앱·옛 APK | 패키지·버전·파일 지문 확인 |
| 앱 재시작 후 장바구니 없음 | 현재 메모리 상태 초기화 | 영구 저장과 구분 |

업데이트 오류를 해결하려고 기존 앱을 먼저 삭제하면 원래 자료를 잃을 수 있다. 오류 문구와 두 APK의 출처를 먼저 확인한다. 개발 서버 없이 실행되는지와 오프라인에서 실행되는지도 따로 검사한다.

# 부록 C 예제 소스코드 사용법

책의 단계 소스는 독자가 비교하고 실습할 수 있도록 나누어 제공한다. 폴더를 새로 만든다고 이전 장의 사용자 수정이 자동으로 합쳐지는 것은 아니다. 각 장 폴더를 보존하고 필요한 변경만 옮긴다.

## C.1 배포 ZIP에서 시작하기

2쪽에서 안내하는 `market-lab.zip`의 1·2장에는 기획 활동지와 개발 도구 점검표, 3~20장에는 개발 예제가 들어 있다. 각 장은 독립된 폴더로 꺼낼 수 있다. 20장에는 완성 앱의 소스코드가 들어 있어 이 장부터 열어도 된다.

### 처음 푼 ZIP에서 완성 앱을 한 줄로 실행하기

준비물은 2장에서 설치한 Node.js와 인터넷에 연결된 Windows PC다. 아직 20장 폴더를 꺼내지 않았다면 VS Code에서 **처음 압축을 푼 폴더**를 열고 **터미널 → 새 터미널**을 누른다. 아래쪽 탭 오른쪽에 **PowerShell**이 표시되고, `ls start.mjs`를 입력했을 때 파일 이름이 보이는지 확인한다. 앞 장을 거치지 않고 다음 **한 줄**을 입력할 수 있다.

~~~powershell
cmd /c "node start.mjs 20 && cd work\ch20\apps\mobile && npm ci && npm run web"
~~~

화면 너비에 따라 명령이 두 줄로 보일 수 있다. 마지막 큰따옴표까지 입력한 뒤 Enter를 한 번 누른다. Windows의 `cmd /c`가 따옴표 안의 명령을 차례대로 실행한다. 앞 명령이 성공하면 다음 명령으로 넘어가면서 **20장 꺼내기 → 앱 폴더로 이동 → 패키지 설치 → 브라우저 열기**까지 진행한다.

브라우저에서 **예시 상품으로 바로 놀이하기**를 누른다. **우리 가게 물건 · 12가지**가 보이면 완성 앱을 연 것이다. 2.6절의 그림 2-23~2-28에서 터미널과 브라우저를 차례로 비교해 볼 수 있다.

**이미 20장 폴더를 열었다면** VS Code 탐색기에서 `work/ch20/apps/mobile`의 **mobile**을 오른쪽 클릭해 **통합 터미널에서 열기**를 누른다. 처음이면 PowerShell에서 `npm.cmd ci`를 한 번 실행한다. 설치가 끝난 뒤에는 **`npm.cmd run web` 한 줄**로 브라우저를 연다. Git Bash에서는 각각 `npm ci`, `npm run web`을 사용한다.

## C.3 잠금 파일로 설치하기

각 단계 앱 폴더의 `package.json`과 `package-lock.json`은 한 쌍이다. 아래 명령은 방금 꺼낸 장 폴더에서 입력한다. 20장을 꺼냈다면 `work/ch20`이다. VS Code 왼쪽에서 해당 장 폴더를 오른쪽 클릭해 **통합 터미널에서 열기**를 선택하면 이 위치에서 시작한다. PowerShell에서는 마지막 줄을 `npm.cmd ci`로 입력한다.

```bash
cd apps/mobile
npm ci
```

11장 이후 DB 검사를 사용할 때는 저장소 루트에서 다음도 실행한다.

```bash
npm --prefix scripts/database ci
```

`node_modules`를 다른 장에서 복사해 오는 대신 현재 잠금 파일로 설치한다. 패키지를 추가한 장에서는 두 설정 파일의 차이를 함께 읽는다. 오래된 lock을 삭제하고 무조건 최신으로 재설치하면 책과 다른 조합이 만들어질 수 있다.

본인의 공개 연결값은 각 단계의 `.env.local`에 별도로 준비한다. 다른 사람의 환경 파일을 복사하지 않는다. 환경 변수의 이름은 제공된 `.env.example`과 해당 장을 따른다.

## C.4 과거 Git 소스를 별도 폴더에서 읽기

기존 프로젝트의 Git 이력이 있는 독자는 원본 저장소 루트에서 다음처럼 별도 복사본을 만들 수 있다.

```bash
git cat-file -t 35b12e4
git clone --no-local . ../market-book-reference
cd ../market-book-reference
git switch --detach 35b12e4
```

첫 명령이 `commit`을 출력하는지 먼저 확인한다. 커밋이 없다면 해당 이력이 포함된 예제 소스가 필요하다. 이름이 같은 폴더가 있으면 다른 새 이름을 사용한다.

detached HEAD에서는 특정 커밋의 코드를 읽고 실행할 수 있다. 자신의 작업을 이어 저장하거나 17장의 Git 보호 검사를 쓸 경우 새 브랜치를 만든다.

```bash
git switch -c codex/book-reference
```

이 작업은 복사본에서 한다. 원본 작업 폴더를 과거 커밋으로 되돌리는 과정이 아니다. 태그를 만들거나 원격 이력을 바꾸는 명령도 필요하지 않다.

## C.5 두 파일 비교하기

VS Code 탐색기에서 이전 파일을 오른쪽 클릭해 **비교 대상으로 선택**한다. 이어 새 파일을 오른쪽 클릭해 **선택한 항목과 비교**를 누른다. 빨간 부분과 초록 부분을 읽고 역할을 구분한다.

1. 파일이 이동한 것인가, 함수 이름이 달라진 것인가.
2. 입력 props와 반환값이 바뀌었는가.
3. 검사에서 사용하는 `testID`가 바뀌었는가.
4. 새 패키지가 추가되었는가.
5. 내 수정 중 실제로 유지할 부분은 무엇인가.

Git 이력에서 변경 파일 목록을 읽을 수도 있다.

```bash
git diff --stat c949154 97b00ff -- apps/mobile
git diff c949154 97b00ff -- apps/mobile/App.tsx apps/mobile/src
```

두 번째 명령에 차이가 없으면 앱 코드가 같은 것이지 두 커밋의 모든 파일이 같다는 뜻은 아니다. 검사 도구나 문서는 별도로 달라질 수 있다.

## C.6 Git Bash에서 변경을 커밋하고 GitHub에 올리기

Git Bash에서 [2.7절](#ch02-s7)의 연습 저장소로 이동한다. 두 번째 명령이 내 `market-book/market-notes` 폴더를 가리키는지 확인한다.

~~~bash
cd ~/market-book/market-notes
git rev-parse --show-toplevel
~~~

### 1. 변경 확인하고 커밋할 파일 고르기

VS Code에서 원본 `prices.ts`의 사과 가격을 `1500`에서 `1800`으로 바꾸고 저장한다. Git Bash로 돌아와 다음 세 줄을 실행한다.

~~~bash
git status
git diff -- prices.ts
node prices.ts
~~~

`git status`에서 `modified: prices.ts`, 실행 결과에서 `사과 1800`을 확인한다. `git status --short`는 파일 상태를, `git diff --stat`은 스테이징 전 변경량을 짧게 보여 준다. 이제 다음 커밋에 넣을 파일을 고른다. 이렇게 골라 두는 것을 **스테이징**이라고 한다.

~~~bash
git add -- prices.ts
git status
git diff --cached
~~~

두 번째 `git status`에서는 `prices.ts`가 **Changes to be committed** 아래로 옮겨간다. 2.7절에서 만든 `prices-copy.ts`는 **Untracked files**에 그대로 둘 수 있다. `git diff --cached`로 이번에 기록할 변경이 사과 가격 한 줄인지 확인한다.

### 2. 내 PC에 커밋하고 내용 읽기

~~~bash
git commit -m "연습용 사과 가격을 1800원으로 변경"
git show HEAD
~~~

`git commit`은 스테이징한 내용을 메시지와 함께 내 PC에 기록한다. `HEAD`는 지금 보고 있는 커밋을 뜻한다. `git show HEAD`에서 커밋 번호와 메시지, `-` 줄의 이전 값 1500과 `+` 줄의 새 값 1800을 확인한다. 긴 출력 맨 아래에 `(END)`가 보이면 **q**를 눌러 터미널로 돌아온다.

### 3. 내 GitHub 저장소에 올리기

~~~bash
git branch --show-current
git remote -v
~~~

첫 줄에서 현재 브랜치 이름을 읽는다. 두 번째 줄에 `origin`이 보이면 `(push)` 옆 주소가 내가 올릴 GitHub 저장소인지 확인한다. 2.7절처럼 PC에서 `git init`만 했다면 보통 두 번째 줄의 출력이 비어 있다. 이 경우 GitHub에서 내 계정에 README·라이선스·.gitignore 없이 빈 `market-notes` 저장소를 만든다. 저장소의 HTTPS 주소를 복사해 아래 따옴표 안의 글자를 통째로 바꾼다. 이 연결은 한 번만 설정한다.

~~~bash
git remote add origin "복사한 HTTPS 주소"
git remote -v
~~~

올릴 주소를 확인했으면 다음 명령을 실행한다.

~~~bash
git push -u origin HEAD
git rev-parse --short HEAD
~~~

`git push`가 현재 브랜치의 커밋을 GitHub에 올린다. 첫 업로드의 `-u`는 로컬 브랜치와 원격 브랜치의 연결을 기억한다. 다음 커밋부터는 같은 브랜치에서 `git push`만 입력해도 된다. 브랜치 이름이 `main`이면 `git push origin main`처럼 대상을 직접 적을 수도 있다. GitHub에서 방금 올린 브랜치를 선택하고, 최신 커밋 번호의 앞부분과 메시지가 내 PC의 기록과 같은지 확인한다.

### 개발 기록에 남길 내용

- 바꾼 이유와 파일.
- 실행한 명령과 실제 결과.
- 기기에서 확인한 모델·버전·앱 빌드.
- 실패한 조건과 해결.
- 확인하지 않은 범위.

비밀번호·서명 키·비공개 가격 원자료·개인 화면은 소스 이력에 넣지 않는다. 공개 보고서에는 필요한 결과만 남기고 원본 로그와 화면은 `.artifacts` 등 개인 보관 영역으로 구분한다. 로컬 커밋을 만들었다는 사실과 GitHub 업로드가 끝났다는 사실도 따로 기록한다.
